| 1 | `machine_learning_files/merge_pipeline.py` (`compute_event_features`) | **Regression from PR #26.** That PR changed `ev_ts.dt.tz_localize(None)` / `ts_series.dt.tz_localize(None)` to `.tz_convert(None)`, on the claim that `tz_localize(None)` raises `TypeError` on a tz-aware Series in pandas ≥ 0.24. Verified empirically on pandas 3.0.3 (this repo pins `pandas>=2.1.0`) — it does **not** raise; it correctly strips the tz while keeping the local wall-clock value. `tz_convert(None)` instead converts to the UTC-equivalent instant first, shifting the value by the UTC offset (verified: a `2024-01-31 21:00 America/Los_Angeles` game becomes `2024-02-01 05:00` naive) — silently reclassifying late-night home games into the wrong month for the `is_game_day`/event-count features. Reverted both call sites back to `tz_localize(None)`. | High — corrupts the event/game-day features fed to every model that uses them |
| 2 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | Same root bug, but pre-existing (not from any daily-audit PR — original author code, untouched since introduction): `tz_convert(None)` on the loaded weather timestamp shifts by the UTC offset before year/month bucketing in the monthly weather aggregation, misattributing readings taken late at night to the wrong day/month. Changed to `tz_localize(None)`. | Medium — skews which month's average temp/precip/wind a given month "sees" |
| 3 | `models/baselines/scheduler.py` | Three inline nightly-scheduler steps import from packages that don't exist in this repo: `step_fetch_weather()` imports `ingestion.fetch_weather_openmeteo`, `step_fetch_events()` imports `ingestion.fetch_events`, `step_validate()` imports `processing.validators` — there is no `ingestion/` or `processing/` package anywhere in the tree. Corrected to `machine_learning_files.fetch_weather_openmeteo`, `machine_learning_files.fetch_events`, and `evaluation.validators` (confirmed these are the actual module locations and that the imported names — `OpenMeteoClient`, `fetch_forecast_all_stations`, `load_config`, `fetch_all`, `validate_feature_store`, `ValidationMode` — exist there). | High — three of the scheduler's inline pipeline steps were silently no-ops |

## Process note

Two of today's three fixes exist because a previous automated pass "fixed" a crash that doesn't
actually happen, based on the tz_localize/tz_convert distinction without testing it against a
real pandas install. Recommend that future daily passes actually execute a minimal repro
(`pip install pandas` + a 3-line script) before asserting a pandas API raises/doesn't raise,
rather than reasoning from the function name — `tz_localize(None)` and `tz_convert(None)` are
easy to conflate but have materially different (and both "valid", non-crashing) semantics.
