# Daily Update — 2026-06-30

## Bug Fixes

### 1. `evaluation/metrics.py` — Falsy check silently drops `0.0` metric values
**Location:** `MetricsReport.to_dict()`, lines 162–164  
**Problem:** `if self.mase`, `if self.coverage`, and `if self.int_width` evaluate to `False` when the metric value is `0.0`, causing a perfect score (MASE=0) or zero-width interval to be reported as `None` instead of the actual value.  
**Fix:** Changed all three checks to `if self.mase is not None`, `if self.coverage is not None`, `if self.int_width is not None`.

---

### 2. `machine_learning_files/merge_pipeline.py` — `tz_localize(None)` on tz-aware Series
**Location:** `compute_event_features()`, lines 184–185 and 191–192  
**Problem:** After `load_events()` localizes event timestamps to `America/Los_Angeles`, calling `.dt.tz_localize(None)` on the already-tz-aware Series raises `TypeError` in pandas ≥ 0.24. This breaks the event feature join entirely when events are present.  
**Fix:** Changed both occurrences to `.dt.tz_convert(None)`, which correctly strips timezone info while preserving local-time values.

---

### 3. `machine_learning_files/merge_pipeline.py` — Timezone mismatch in date range filter
**Location:** `build_feature_store()`, lines 313–316  
**Problem:** The `--start` / `--end` date filter constructed tz-aware `pd.Timestamp` objects (`tz="America/Los_Angeles"`) and compared them against `base["timestamp"]`, which is tz-naive (originating from `pd.to_datetime(station_monthly["period"])`). Mixing tz-aware and tz-naive raises `TypeError`.  
**Fix:** Replaced the hard-coded tz-aware construction with logic that checks the actual tz-awareness of `base["timestamp"]` and only adds timezone if the column has one.

---

### 4. `Processing/feature_engineering.py` — Dead `n_new` variable always equals 0
**Location:** `build_features()`, lines 441–443  
**Problem:** `n_new = n_features - len(df.columns)` was always `0` because `n_features` was assigned `len(df.columns)` on the same line immediately before. The original column count was never captured prior to the feature-engineering calls, making this a no-op computation.  
**Fix:** Captured `n_input_cols = len(df.columns)` before the transformation calls and used `n_new = n_features - n_input_cols`. Also updated the log message to show `+N new` columns.

---

### 5. `models/baselines/arima.py` — Wrong seasonal period for monthly data in `fit_auto_arima()`
**Location:** `fit_auto_arima()`, line 185  
**Problem:** `s = 24 if "h" in freq.lower() else 96` gave `s=96` for monthly frequency (`"MS"`), telling pmdarima to search for a 96-step (8-year) seasonal cycle instead of the correct 12-month annual cycle. This would produce a badly-specified auto-ARIMA model for monthly BART OD data.  
**Fix:** Added an explicit monthly check: `s=12` for `"MS"/"month"/"M"`, `s=24` for hourly, `s=96` for all other (15-min) frequencies.

---

### 6. `evaluation/validators.py` — Fragile index arithmetic in gap detection
**Location:** `check_missing_windows()`, line 174  
**Problem:** `grp.loc[idx - 1, "timestamp"]` assumed the DataFrame's integer index was contiguous. When the original DataFrame index has gaps (e.g., rows at labels 0, 2, 7, 10…), `idx - 1` refers to a label that may not exist or may be an unrelated row, producing incorrect gap-start timestamps or silently returning `"unknown"` when the start was knowable.  
**Fix:** Changed to positional indexing: `pos = grp.index.get_loc(idx)` and `grp.iloc[pos - 1]["timestamp"]`, which correctly retrieves the row preceding the gap regardless of label values.
