### New bugs found and fixed today

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/ablation.py` (`COVARIATE_GROUPS["weather"]`) | `weather_code` (a real trained-model covariate — part of `finetune.py`'s `KNOWN_FUTURE_COLS`) was missing from `ablation.py`'s own weather covariate-group list. This is the same "drifted duplicate covariate-list" bug class already fixed twice elsewhere in this repo (`finetune.py`'s known-covariate lists, `merge_pipeline.py`'s weather aggregation), recurring a third time. Since `zero_out_groups()` only zeroes columns present in `COVARIATE_GROUPS`, `weather_code` was never neutralized for *any* ablation config — including `"1_baseline"`, which is supposed to run with zero covariates. Every ablation config silently leaked a real weather signal, invalidating the study's baseline-vs-full comparison. Fixed by adding `"weather_code"` to the weather group. | Medium |
| 2 | `Processing/ablation.py` (`run_inference_with_config`) | The check gating whether `known_covariates` gets built compared `len(future_df)` — a row count summed across *all* stations — against `prediction_length`, instead of checking per station. With uneven per-station history (e.g. a station added partway through the feature store), this can pass in aggregate while one station individually has fewer than `prediction_length` future rows, producing a ragged known-covariates frame; AutoGluon requires every item to have full-horizon coverage. Fixed by checking `future_df.groupby("item_id").size().min() >= prediction_length` instead of the aggregate row count, and reporting the true per-station shortfall in the fallback warning. | Low-Medium |
| 3 | `models/chronos2/predict.py` (`Predictor._ensure_loaded`) | When `force_mode="finetuned"`/`"zeroshot"` is passed but the corresponding backend fails to load (`_load_finetuned()`/`_load_zeroshot()` returns `False`), the method still returned the requested mode string anyway. `forecast()` dispatches on that string and calls `_finetuned_forecast`/`_zeroshot_forecast`, which dereference `self._predictor`/`self._pipeline` — both still `None` — crashing. Currently masked because the only caller (`benchmarks.py`) wraps the call in `try/except` and pre-checks the finetuned-weights directory, but this is the same entry point `api.py`/`scheduler.py` use. Fixed: on load failure, return `"naive"` (already handled by `forecast()`) instead of a mode with no backend loaded. | Low |
| 4 | `transit_eda/notebooks/eda_complete.ipynb` (`plot_rain_vs_ridership`) | `sub = df[df["precip_mm"] > 0].sample(min(5000, len(df)), ...)` computed the sample cap from `len(df)` (the full, unfiltered frame) but sampled from the filtered subset. Whenever the filtered subset is smaller than that cap — true whenever any row has `precip_mm <= 0` on a large `df` — raises `ValueError: Cannot take a larger sample than population when 'replace=False'`. Currently dormant only because every row in the checked-in 1,800-row monthly feature store happens to have `precip_mm > 0`; would break immediately under more realistic or hourly-cadence data (the latter is an explicit roadmap item per `docs/ARCHITECTURE.md`). Fixed by computing the cap from the filtered subset's own length. | Medium |

## Known issues logged (not fixed today)

- **The stale/duplicate PR backlog remains the project's actual blocker** —
  23rd consecutive daily log making this same recommendation, now against

- `Processing/feature_engineering.py`'s `add_weather_features`:
  `precip_3hr_sum`/`precip_6hr_sum`/`precip_24hr_sum`/`is_rain_onset` are
  computed with fixed-size 3/6/24-row rolling windows and named/documented
  as hour-scale ("past N hours", "first hour of rain after a dry spell").
  At the pipeline's actual monthly cadence these windows instead span
  trailing *months*, not hours — the same bug class already fixed for
  `is_am_peak`/`is_pm_peak` and the event-proximity windows elsewhere in
  this repo. Not fixed today: unlike those prior cases, it isn't provably a
  dead/constant signal without pandas available in this sandbox to check
  against real data (monthly-mean Bay Area precipitation is rarely exactly
  ≤0, so `is_rain_onset` may not be constant-False the way the hour-scale
  peak/event flags were) — redesigning the semantics without being able to
  verify against real data risked an incorrect fix. Worth checking with
  real data available.
