## Bugs fixed today (new — previously unaudited code)

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `transit_eda/notebooks/eda_complete.py` (Section 4D, Lorenz-curve panel) | `sorted_exits`/`cumulative` are built ascending (weakest station first), so `cumulative[top20_idx]` at `stations_pct == 80` is the exit share held by the **bottom** 80% of stations, not the top 20%. The annotation labeled this value `"Top 20% of stations = {…:.0f}% of exits"` — backwards. For a right-skewed distribution this silently reported e.g. "top 20% of stations = 30% of exits" when the real top-20% share is `100 - bottom80_share` (~70%), inverting the intended Pareto/H1 headline stat in the generated `s4a_demand_distribution.png` figure. Fixed by computing `top20_share = 100 - bottom80_share` and annotating that instead. | Medium |
| 2 | `transit_eda/notebooks/eda_complete.ipynb` (Cell 2, setup) | `os.chdir('/Users/dhruvshah/Desktop/transit-demand-forecasting')` — a hardcoded personal machine path. Crashes with `FileNotFoundError` for anyone else (or any CI/automation) running the notebook. Replaced with a repo-root search that walks up from the notebook's cwd looking for a `machine_learning_files/` marker directory, raising a clear error only if the notebook truly isn't launched from inside the repo. | Low-Medium |
| 3 | `transit_eda/notebooks/eda_complete.ipynb` (Cell 2, setup) | `PLOTS_DIR = Path('eda/plots')` points at a directory that doesn't exist anywhere in the repo. The images this notebook's `_save()` helper actually names (`01_ridership_overview.png`, `02_monthly_heatmap.png`, …) already exist in `website/data/eda_plots/` — the directory the live site actually serves from. Re-running the notebook silently wrote a fresh, orphaned `eda/plots/` tree instead of updating production output. Fixed by pointing `PLOTS_DIR` at `website/data/eda_plots`. | Medium |

- `transit_eda/notebooks/eda_complete.ipynb`'s Plots 03/04/09
  (`plot_dow_distribution`, `plot_sharks_game_spike`,
  `plot_seasonal_decomposition`) derive `day_of_week`/`hour_of_day` via
  `.dt.dayofweek`/`.dt.hour` and resample to hourly/weekly cadence,
  assuming sub-daily data. The feature store this notebook loads is
  monthly-cadence (same root cause as the already-logged `is_am_peak`/
  event-window bugs in `Processing/`), so every timestamp is
  midnight-of-month: `hour_of_day` is always 0 and `day_of_week` only
  reflects whichever weekday the 1st of each month falls on. These plots
  degrade silently (non-representative distributions) rather than
  crashing, so left as a logged issue rather than a same-day fix — a
  correct repair needs a cadence-aware fallback (mirroring the pattern
  already used in `Processing/feature_engineering.py`) applied consistently
  across all three plot functions, which is more scope than a single-day
  audit item.
