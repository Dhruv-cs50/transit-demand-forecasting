Found and independently re-verified two new bugs before fixing:

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/fetch_weather_openmeteo.py` / `machine_learning_files/merge_pipeline.py` (`load_weather`) | `fetch_forecast_all_stations()` — the nightly-scheduler step (`scheduler.py`'s `step_fetch_weather`) that pulls the 7-day-ahead Open-Meteo forecast — writes to `data/raw/weather/weather_forecast_{run_ts}.parquet`. `load_weather()` only globbed `weather_all_stations_*.parquet`, a filename pattern produced solely by the separate historical-backfill function. The entire nightly "future weather" pipeline step ran successfully and fetched real data that `build_feature_store()` could never see — silently dropping every future-known weather covariate with no error or warning, only missing/NaN downstream. Fixed by also globbing `weather_forecast_*.parquet` and concatenating the most recent file of each kind (`get_historical`/`get_forecast` share the same `_to_dataframe` schema, confirmed by reading `fetch_weather_openmeteo.py`). | High |
| 2 | `models/chronos2/predict.py` (`Predictor._ensure_loaded`) | When `force_mode` is passed (used by `benchmarks.py`'s zero-shot/fine-tuned leaderboard sections, added by the 2026-07-16 fix for the singleton-mislabeling bug), `self._mode` was set to `force_mode` unconditionally — even when `_load_finetuned()`/`_load_zeroshot()` returned `False` on failure (missing/incompatible weights, `chronos-forecasting` not installed). `forecast()` then dispatches on `self._mode` and calls `self._predictor.predict(...)` / `pipeline.predict_df(...)` on `None`, raising `AttributeError`, bypassing the graceful `"naive"` fallback the non-forced path already uses. `forecast_all_stations()` catches this per-station, so a whole model silently vanishes from the benchmark leaderboard (the same leaderboard that feeds the website's headline model-comparison numbers) instead of falling back to naive. This is a fresh regression introduced by the `force_mode` fix itself, not a re-flagged old bug. Fixed by only committing `self._mode = force_mode` when the load actually succeeded, falling back to `"naive"` with a warning otherwise — matching the non-forced path's behavior. | Medium |

Both were independently re-verified by reading the exact current file
contents and tracing the call path (`scheduler.py` → `fetch_weather_openmeteo.py`
for #1; `benchmarks.py` → `predict.py` for #2) before fixing, not copied
from a report.
