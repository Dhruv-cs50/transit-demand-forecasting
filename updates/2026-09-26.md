None of these writes are atomic (plain `df.to_parquet(path)`, no write-to-temp-then-rename), so a killed process, OOM, or full disk during a prior write is a realistic way to leave a truncated/corrupt file at the final path — not a hypothetical. Verified live with synthetic corrupt-file repros: (a) `load_transit()` with one good BART OD month + one corrupt month → before, `ArrowInvalid` aborted the whole `build_feature_store()` call; after, the corrupt file is logged, deleted, and skipped, and the good month's row still loads. (b) Same pattern confirmed for `load_weather()` (a corrupt file in a multi-file `hist_files` group) and `load_events()`. (c) `fetch_bart_od.py::fetch_all(2019, 2019)` with a good Jan cache file and a corrupt Feb cache file: before, the crash on Feb's cache read meant **March–December were never even attempted** (confirmed via a monkeypatched `download_month()` — the corrupt Feb file silently killed every remaining month in the batch, not just Feb); after, Feb's corrupt cache is deleted and re-downloaded, and all of March–December are still attempted. Also added an explicit empty-`DataFrame` return (instead of an `IndexError`/crash) for the case where *every* file in a group is corrupt. Fixed via a shared `_read_parquet_safe()` helper in `merge_pipeline.py` and an inline try/except in `fetch_bart_od.py` (mirroring the existing `download_month()`/`fetch_pems_bay_dataset()` style). | Medium-High |
