| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/feature_engineering.py` (`add_event_features`, tz-normalization loop) | The tz-awareness normalization loop covered `df["timestamp"]` and `events["timestamp_start"]` but never `events["timestamp_end"]`. The same bug class fixed repeatedly elsewhere in this codebase (tz-mixing), but via a missed column rather than the usual `tz_convert(None)` mistake: if `timestamp_end` ever arrives tz-naive while the other two columns are/become tz-aware, the later `.values` extraction UTC-converts the tz-aware columns while leaving `timestamp_end` at naive LA wall-clock, silently offsetting `is_post_event_window`, `hours_since_last_event`, and the post-event `event_proximity_score` by the LA-UTC offset (7-8h). Reproduced with a synthetic events/df pair: old code misreported an event that ended 1.5h ago as having ended ~9.5h ago, flipping `is_post_event_window` from `True` to `False`. Currently dormant — `fetch_events.py` has written `timestamp_end` tz-aware since the 2026-08-28 Ticketmaster fix — but a real defect in the function's own contract, fixed for the same "before it can silently reappear" reason as the 2026-08-26 `load_weather` tz-strip fix. Fixed by including `timestamp_end` in the same normalization loop. | Medium (latent) |
| 2 | `models/baselines/benchmarks.py` (`seasonal_naive_forecast`) | `repeated = np.tile(last_week, ...)` is built assuming positional row *i* is the *i*-th chronological test timestamp for that station, then assigned to `grp["p50"]` positionally — but `grp` (from `test_df.groupby("station_id")`) was never sorted by timestamp, unlike `train_grp` two lines above (which is) and every sibling file in this audit area (`predict.py`, `zero_shot.py`, `ablation.py` all explicitly re-sort by timestamp after filtering by station for exactly this reason). If a station's on-disk row order isn't chronological, every test timestamp gets paired with the wrong seasonal-naive value — silently corrupting the SeasonalNaive baseline that this file's own docstring says "is what powers the MAPE 11.8% number on your website hero," and the Diebold-Mariano significance test that compares AutoGluon against it. Reproduced with a synthetic shuffled-row `test_df`; confirmed the exact month-misalignment and that it's resolved after sorting. Fixed by sorting `grp` by `timestamp` before the positional assignment. | Medium |
| 3 | `models/chronos2/predict.py` (`Predictor._naive_forecast`) | `period = int(pd.tseries.frequencies.to_offset(freq).nanos / (3600 * 1e9)) * 168` truncates hours-per-step to `int()` *before* multiplying by 168. For any sub-hourly frequency (e.g. `15min`, hours-per-step = 0.25), `int(0.25) = 0`, so `period = 0`, and the subsequent `i % period` raises `ZeroDivisionError` — crashing this emergency naive-forecast fallback (used when neither AutoGluon nor Chronos load) the instant `resample_freq` is sub-hourly, despite the code's own comment documenting sub-hourly support ("at 15min → 672 steps") that was never actually reachable. Currently latent: `configs/model.yaml` hardcodes `resample_freq: "MS"` (monthly), which takes a separate branch entirely. Verified `int(0.25)*168 == 0` directly and that the fixed formula (`max(1, round(168/hours_per_step))`) produces 672 for 15min and 168 for hourly, matching the documented intent. Fixed by computing `hours_per_step` first, then dividing 168 by it before rounding. | Low (latent) |
