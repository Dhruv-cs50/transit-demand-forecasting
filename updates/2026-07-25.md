## New bugs found today (previously unaudited)

Delegated a broad read-only sweep of `models/baselines/*.py`,
`evaluation/*.py`, `machine_learning_files/fetch_weather_openmeteo.py`,
`models/chronos2/finetune.py`, `configs/*.yaml`, `website/tweaks-panel.jsx`,
`website/api-demo.html`, `scripts/export_website_data.py`, plus a
cross-file consistency check of `KNOWN_FUTURE_COLS`/`known_covariates` now
that it's shared across `ablation.py`, `predict.py`, and `finetune.py`.
Found 3 candidates; 2 independently re-verified and fixed (one with a
minimal pandas repro), one confirmed real but left as a known issue
(already logged and deliberately deferred yesterday — see below).

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 16 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`) | `base = transit_df.copy()` inherited `load_transit()`'s gapped index (the "Exits"-style aggregate-row filter there drops rows via a boolean mask with no `reset_index()`). `matched = base.merge(...)` and `fallback = base.merge(...)` are plain `pd.merge()` calls, which always return a fresh `0..n-1` `RangeIndex` regardless of the left frame's index — so `base[col] = matched[col].where(has_match, fallback[col])`'s label-based alignment silently paired each row with a *different* row's weather value (confirmed with a minimal repro: a station ended up with a neighboring station's weather, and the last row got `NaN` because the merge result's index ran short of `base`'s gapped labels). This corrupted `temp_f`, `precip_mm`, `windspeed_mph`, `is_raining`, `weather_code`, `cloud_cover_pct` — all `KNOWN_FUTURE_COLS` members — across most of the feature store, with no error raised. Fixed by resetting `base` to a clean `0..n-1` index right after the copy, before any of the merge/where logic runs. | High |
| 17 | `Processing/ablation.py` (`COVARIATE_GROUPS["weather"]`) | `weather_code` is a real feature-store column (`finetune.py`'s `KNOWN_FUTURE_COLS` includes it) but was missing from `COVARIATE_GROUPS["weather"]`. Since `zero_out_groups()` only zeroes columns listed in `COVARIATE_GROUPS`, the `1_baseline`/`2_plus_calendar` ablation configs — meant to exclude weather entirely — still fed the model real `weather_code` values, inflating those baselines' apparent accuracy and understating weather's true contribution in `ablation_impact.csv`. Added `weather_code` to the group. | Medium |

## Known issues logged (not fixed today)

- The stale/duplicate PR backlog remains the actual blocker on this
  project — see "Backlog status" above. Eleventh consecutive daily log
  making this recommendation; 44 open PRs, zero merges since 2026-07-16.
- `machine_learning_files/api.py`'s `_run_forecast` slow path and
  `models/chronos2/predict.py`'s `Predictor.forecast()` both compute
  `prediction_length`/`horizon_steps` purely from
  `configs/model.yaml`'s `forecast_horizon_steps: 6` and never apply the
  caller-supplied `horizon_hours` — unlike the cached fast path, which
  truncates via `.head(horizon_hours)`. Independently re-confirmed today
  (third time flagged); first logged and deliberately left unfixed
  2026-07-24 because a correct fix requires deciding what "N hours" even
  means at this pipeline's monthly cadence (the old
  `steps_per_hour = freq.nanos / 3600e9` conversion `ablation.py` used to
  have has no fixed nanosecond duration for `"MS"` and only worked via an
  approximate 30-day-month fallback) — a real design decision, not a
  one-line patch. No observable effect today since neither the website nor
  `api-demo.html` reads the field this would change.
- `evaluation/validators.py` defines `EXPECTED_DTYPES`, `MAX_IMPUTED_ROWS`,
  and `WEATHER_MAX_AGE_HOURS` but no check function ever references them —
  unimplemented scope, not incorrect behavior. Unchanged since first
  flagged 2026-07-23.
- `Processing/feature_engineering.py`'s `add_station_features()` —
  `dist_from_diridon_km`/`in_event_catchment` remain permanently dead; no
  code path supplies per-station `lat`/`lng`. Unchanged since first flagged
  2026-07-22 — still needs a real `station_id → (lat, lng)` lookup, not
  code logic.
- `machine_learning_files/fetch_weather_openmeteo.py` fetches
  `humidity_pct` but `merge_pipeline.py`'s monthly aggregation never keeps
  it — dead column, silently guarded downstream.
- `Processing/ablation.py`'s `zero_out_groups()` still leaves
  `object`-dtype columns (currently only `transit_mode`) unneutralized —
  zero observable effect today since `transit_mode` is constant.
- `models/baselines/fetch_pems_roads.py` remains unwired into the
  pipeline (per `merge_pipeline.py`'s own docstring) — no runtime effect.
