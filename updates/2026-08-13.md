# Daily Update — 2026-08-13

## Backlog status

`main` is still current only through PR #42 (merged 2026-07-16 — **28 days
ago**). **63 open PRs** (#2–#69, excluding already-merged ones) sit
unreviewed; the count has grown every single day this figure has been
tracked (36 → 49 → 61 → 64 → 63 today, roughly flat only because a couple
were likely closed as duplicates).

Per yesterday's finding (`updates/2026-08-12.md`), this backlog is not just
unreviewed — large parts of it are **mutually inconsistent**, because each
day's branch has historically been built from stale `main` plus only the
*immediately preceding* day's reapplication, so fixes that land on day N but
aren't carried forward verbatim silently fall out of the lineage. This
branch breaks that pattern the same way yesterday's did: it was built by
fast-forwarding onto **PR #69**'s actual tip commit (`afc7261`, 2026-08-12,
the newest open PR) rather than stale `main`, so all 15 of #69's fixes (and
everything they carried forward from #68/#67/...) are present here, plus
the 5 new fixes below.

**Recommend, unchanged from yesterday:** merge this PR (or #69) into `main`
now, then close the #2–#68 backlog as superseded rather than trying to
reconcile 60+ stale branches by hand — a fresh audit against a clean merged
`main` is cheaper than that reconciliation, and is what tomorrow's run would
do anyway.

## Bugs fixed today

Three independent parallel audits, each scoped to a different subsystem
(data ingestion/feature pipeline, modeling/evaluation, API/website/config),
each given yesterday's fix list and "verified clean" list up front to avoid
re-reporting known-fixed items. All 5 findings below were independently
re-verified against the actual current file contents (not prior PR
descriptions) before fixing, and the 3 touched Python files re-checked with
`python3 -m py_compile` after.

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`) | `load_transit()` drops non-station aggregate rows (BART's "Exits"/"Entries" totals) via a boolean mask, leaving `transit_df`'s index non-contiguous. `build_feature_store`'s weather-merge step then reassigns fresh-indexed `.merge()` results (`matched`, `fallback`) back onto `base` via `base[col] = matched[col].where(has_match, fallback[col])`, which label-aligns on the (gappy) index instead of matching positionally — silently scrambling, cross-assigning, or nulling out most rows' weather covariates on every real run (aggregate rows are always present in production data). Reproduced standalone: confirmed 3 of 5 example rows got wrong values before the fix. Fixed with `base = transit_df.copy().reset_index(drop=True)`. | High |
| 2 | `models/chronos2/predict.py` (`_finetuned_forecast`, `_zeroshot_forecast`) | The quantile-column rename mapped both the `"0.5"` quantile column *and* AutoGluon's separate `"mean"` column to `"p50"` — both columns exist simultaneously in real `TimeSeriesPredictor.predict()` output (mean + one column per configured quantile level, and 0.5 is one of the configured levels per `configs/model.yaml`). After `rename()`, the frame carried two columns both named `p50`, silently turning every downstream `preds["p50"]` access (`ridership_lift()`, `benchmarks.py`'s `compute_metrics()`, any merge in `evaluation/metrics.py`) into a 2-column DataFrame instead of a Series. Fixed in both functions: only fall back to `"mean"` when no quantile column already claimed `p50`. | High |
| 3 | `website/charts.jsx` (`ROCCurve`) | Called `r.WAPE_pct.toFixed(1)` unconditionally on data that can legitimately contain `WAPE_pct: null` since yesterday's NaN-guard fix to the exporter — `.toFixed` on `null` throws, crashing the site's headline "WAPE by model" results chart for any model with a NaN WAPE. Confirmed live risk: the committed `website/data/model_comparison.json` already has a null metric for AutoETS today. Fixed with the same `!= null` guard pattern already used elsewhere on this page. | High |
| 4 | `website/sections.jsx` (`BARTForecasts` table) | Same unguarded pattern in a second location — `r.WAPE_pct.toFixed(1)` and `fmt(r.MAE)` called directly while the adjacent `MAPE_pct` cell in the same row was already correctly guarded. Crashes the model-comparison table on a null WAPE, silently prints the literal string `"null"` for a null MAE. Fixed both cells to match the existing guard pattern. | Medium |
| 5 | `scripts/export_website_data.py` (`export_model_comparison`, no-leaderboard fallback branch) | The fallback path (used when `evaluation/outputs/benchmark_leaderboard.csv` is absent) never received yesterday's NaN guard on the leaderboard branch — `mape` can be NaN (empty nonzero slice) and `wape` can be NaN/Infinity (zero-sum denominator), and `json.dump` would emit a bare `NaN`/`Infinity` token, invalid JSON, breaking every website consumer's `JSON.parse()`. Fixed with the same `math.isfinite(...)` guard used in the leaderboard branch. | Medium |

## Known issues logged (not fixed today)

- The backlog-consistency problem remains the project's biggest actual
  risk — 63 open PRs, 28 days since the last merge. See "Backlog status"
  above.
- `configs/model.yaml` still has no `forecast_horizon_hours`/
  `context_length_hours` keys; the 8 call sites across 6 files that
  reference them as a fallback remain unreachable today because the
  step-based keys are always populated. Re-confirmed today, unchanged from
  2026-08-12's log.
- `predict.py`'s `_naive_forecast` and `benchmarks.py`'s
  `seasonal_naive_forecast` both have an inverted `steps_per_hour` formula
  in their else-branch (computes hours-per-step, would `int()`-truncate to
  0 for sub-hourly frequency — a latent `ZeroDivisionError`), but
  `resample_freq` is hardcoded `"MS"` in `configs/model.yaml`, so this
  branch is provably unreachable today. Flagged for whoever eventually adds
  a second cadence.
- `Predictor`'s singleton `_mode` caching could in theory let a
  `force_mode`-forced call pollute a later unforced call in the same
  process, but no current caller mixes forced and unforced `forecast()`
  calls (`benchmarks.py` always passes `force_mode`) — not currently
  exploitable.
- `machine_learning_files/fetch_bart_od.py`'s `YEAR_MONTH_FORMAT` dict is
  unused dead code (`build_url_candidates` hardcodes the same patterns
  directly) — no incorrect behavior, just dead weight.
- `models/chronos2/finetune.py`'s fine-tuning path and `predict.py`'s
  zero-shot fallback path remain unexercised end-to-end (no GPU packages or
  model weights available in this sandbox), consistent with every prior
  log.
