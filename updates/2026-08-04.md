| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 8 | `machine_learning_files/merge_pipeline.py` (`load_transit`) | `bart_dir.glob("bart_od_*.parquet")` matched **both** `fetch_bart_od.py`'s per-month cache files (`bart_od_2023_01.parquet`, …) **and** the consolidated `bart_od_all.parquet` it also writes into the same directory as the final step of its normal, documented `fetch_all()` CLI usage. With no dedup, every month's rows were concatenated and summed twice before the `groupby(["period","origin","origin_name"])["riders"].sum()` — silently ~doubling `ridership`, the actual training target, for every station in `feature_store.parquet` whenever `fetch_bart_od.py` had been run in its standard one-shot mode. Fixed by excluding `bart_od_all.parquet` from the glob — the per-month files alone are a complete, correct source. | **High** |
| 9 | `machine_learning_files/zero_shot.py` (`load_feature_store`) | Hardcoded `feature_store.parquet`, while every other feature-store consumer in the repo (`arima.py`, `benchmarks.py`, `prophet_baseline.py`, `scheduler.py`, `chronos2/predict.py`) prefers `feature_store_enriched.parquet` (event/lag/station features from `feature_engineering.py`) and falls back only if it's missing. `scripts/run_pipeline.sh` produces the enriched store immediately before running `zero_shot.py`, but that output was never consulted — the "performance floor" baseline (per its own docstring) silently ran on a weaker feature set than every model it's meant to be compared against, undermining the whole point of the comparison. Fixed by adopting the same enriched-first-with-fallback pattern used everywhere else. | Medium |
