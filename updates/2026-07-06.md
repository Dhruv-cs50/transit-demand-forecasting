## Bugs fixed today

These are not new discoveries — they're bugs already diagnosed and fixed in the
still-open PR #31, independently re-verified today against real pandas (3.0.3) and
applied directly to this branch so `main` actually gets patched instead of waiting
on a 32nd unmerged draft:

| # | File | Bug | Severity |
|---|------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`load_weather`, `compute_event_features`) | The 2026-06-30 fix (merged in PR #26) changed `.dt.tz_localize(None)` → `.dt.tz_convert(None)` on the theory that `tz_localize(None)` raises `TypeError` on a tz-aware Series. **Verified this is false** — tested directly against pandas 3.0.3 (the version resolved by `requirements.txt`'s `pandas>=2.1.0` pin): `tz_localize(None)` on tz-aware data succeeds and correctly strips the tz label while preserving local wall-clock time (10:00 PST → 10:00 naive). `tz_convert(None)`, by contrast, shifts the clock to the equivalent UTC instant before dropping the label (10:00 PST → 18:00 naive). Since `compute_event_features()` immediately buckets the result by `_year`/`_month`, a late-night local event (e.g. an 11 PM PDT game on Apr 30) gets shifted to `2026-05-01 06:00` and miscounted into the wrong month's `is_game_day`/`is_sharks_game`/game-count features. Reverted all three sites (`load_weather` line 128, `compute_event_features` lines 185 and 191) back to `tz_localize(None)`. | High |
| 2 | `models/baselines/scheduler.py` (`step_fetch_weather`, `step_fetch_events`, `step_validate`) | Three import paths point at modules that don't exist anywhere in this repo: `ingestion.fetch_weather_openmeteo`, `ingestion.fetch_events`, `processing.validators` (there is no `ingestion/` package; the real modules are `machine_learning_files.fetch_weather_openmeteo`, `machine_learning_files.fetch_events`, `evaluation.validators`). Each step catches the resulting `ModuleNotFoundError` in a broad `except Exception`, logs "fetch failed"/"validation failed", and returns `False` — so every nightly scheduler run has been silently skipping weather ingestion, event ingestion, and feature-store validation since this file was written. Fixed all three import paths. | High |
| 3 | `models/chronos2/predict.py` (`_load_zeroshot`) | Imported and called `Chronos2Pipeline.from_pretrained("amazon/chronos-t5-small", ...)`. `chronos-forecasting` does export a real `Chronos2Pipeline` class, but it asserts the checkpoint is an actual Chronos-2 architecture — `amazon/chronos-t5-small` (per `configs/model.yaml`) is a legacy T5-based Chronos-1 checkpoint, the same `model_id` that `machine_learning_files/zero_shot.py` already loads correctly via plain `ChronosPipeline`. So the zero-shot fallback path — the one meant to kick in when the fine-tuned AutoGluon model is missing — would itself crash. Switched to `ChronosPipeline`, matching `zero_shot.py`. | Medium |

| # | File | Bug | Severity |
|---|------|-----|----------|
| 4 | `models/baselines/benchmarks.py` (module docstring said `evaluation/benchmarks.py` — leftover from a move) | `from evaluation.metrics import ...` at the top level, but `scripts/run_pipeline.sh` invokes this file directly as `models/baselines/benchmarks.py` (step 6). When Python runs a file directly, only its own directory (`models/baselines`) goes on `sys.path`, not the repo root — reproduced directly: `python3 models/baselines/benchmarks.py --help` → `ModuleNotFoundError: No module named 'evaluation'`. Since `run_pipeline.sh` has `set -e`, this crashes the entire documented pipeline at the last step. Fixed by invoking it as a module (`python -m models.baselines.benchmarks`) in `run_pipeline.sh`, and updated the file's docstring path/usage examples to match. | High |
| 5 | `machine_learning_files/fetch_events.py` (`enrich_events()`, line 250) | `df["is_playoff"] = df.get("game_type", ...) == "3"` compares against the string `"3"`, but `game_type` is populated from the NHL API's `gameType` field (line 95), which the API returns as an **integer** (1/2/3/4 per the inline comment), not a string. Comparing an int column to `"3"` is always elementwise `False`, so playoff Sharks games are never flagged — a covariate `finetune.py`'s `_default_covariate_cols` explicitly expects as a known-future feature. Fixed by casting to `str` before comparing. | Medium |
| 6 | `machine_learning_files/fetch_511_transit.py` (`get_lines()`, line 84) | Parses `data.get("Content", {})` (no "s"), while the near-identical `get_stops()` two functions above parses `data.get("Contents", {})` (with "s") from the same 511 SIRI-style API family. This asymmetry between two structurally identical response-envelope parsers means `get_lines()` silently returns an empty DataFrame regardless of actual API content. Fixed to match `get_stops()`'s `"Contents"` key. | Medium |
