| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`load_weather`, `load_events`), `Processing/feature_engineering.py` (`main`) | The 2026-09-18 fix changed these loaders from "load only the single most-recent file" to "concatenate every matching file, `drop_duplicates(keep='last')`", with the inline comments claiming this "keeps the most-recently-written value" for overlapping records. That claim was false: `sorted(glob(...))` (the default, no `key=`) sorts by **filename**, not by actual write time — and `fetch_historical_all_stations()`/`fetch_events.py::fetch_all()` embed the CLI `--start`/`--end` date-range args in the filename. If an operator does a legitimate corrective re-fetch of an earlier, narrower window (e.g. `weather_all_stations_2019-01-01_2019-03-31.parquet`, re-run to fix bad sensor readings, or `events_2019-06-01_2019-06-30.parquet` to fix a misclassified game) *after* a wider file already exists on disk (e.g. `..._2019-01-01_2024-12-31.parquet`), the narrow file's name sorts lexicographically *before* the wide file's regardless of which was actually written more recently — so `keep='last'` kept the wide file's **stale/bad** values for every overlapping row instead of the fix. Verified live: wrote a wide weather file with a bad `temp_f=999.0` reading, then 1.1s later wrote a narrower corrective file with `temp_f=58.0` for the same `(timestamp, station)` — `load_weather()` returned the stale `999.0`. Same repro against `load_events()` with a stale vs. corrected `game_type` reproduced the identical failure. Fixed all three call sites (`merge_pipeline.py::load_weather`/`load_events`, `feature_engineering.py::main`'s duplicated events loader) to sort candidate files by `Path.stat().st_mtime` (actual write time) instead of filename before concatenating, so the `keep='last'` dedup now genuinely keeps the most-recently-written row. Re-verified both repros pass with the fix (weather returns `58.0`, events returns the corrected `game_type`). `weather_forecast_*` files (`fetch_forecast_all_stations`, loaded via `forecast_files[-1]`) were checked and are unaffected — that filename embeds a single monotonically increasing run timestamp, not a date *range*, so filename order and write order always agree there. | Medium-High |
