## Considered but not changed

- `Processing/feature_engineering.py`'s `add_station_features()` computes
  `dist_from_diridon_km`/`in_event_catchment` (the "stations within 5km of
  SAP Center" flag this module's own docstring calls out as core to the
  project's stated Sharks-game/Diridon-VTA-spike value proposition) gated on
  `if "lat" in df.columns and "lng" in df.columns:` — but **no file anywhere
  in the pipeline ever attaches per-station `lat`/`lng` columns**.
  `merge_pipeline.py`'s `build_feature_store()`/`load_transit()` (the sole
  producer this function runs on in the real pipeline, per
  `scripts/run_pipeline.sh`) carries only `station_id`/`station_name`/
  `agency_id`/`transit_mode`; the weather merge explicitly keeps only
  `weather_cols` (never lat/lng, even though `fetch_weather_openmeteo.py`'s
  raw rows carry lat/lng — for the weather-monitoring point, not the
  station); `fetch_bart_od.py`'s `STATION_NAMES` has names only, no
  coordinates. Confirmed with a direct repro against `add_station_features()`
  fed a frame shaped like real `merge_pipeline.py` output: neither column is
  ever added. No crash — a silent, structural dead-feature bug, more
  fundamental than a missing entry in a covariate list (yesterday's fix
  class): there is currently no code path in this repo that could populate
  these two columns for any station. It also means `Processing/ablation.py`'s
  `"station"` covariate group and `event_catchment_stations` slice remain
  silent no-ops even after 2026-09-04's ablation fix, since the enriched
  store it backfills from never has `in_event_catchment` either. **Not
  fixed today**: closing this gap needs a real per-station coordinate
  table (BART/VTA/Caltrain stop lat/lng) added to the pipeline — a data
  curation task, not a pure code fix, and one where a unilaterally
  fabricated coordinate table would risk silently *wrong* distances rather
  than silently *missing* ones. Flagging for the project owner to supply
  or source a real station-coordinates dataset.
