## Known issues logged (not fixed today)

- **New, high-priority:** even after today's fix #1, `models/chronos2/predict.py`'s
  `_finetuned_forecast()` cannot actually complete a true forward forecast in
  production. `build_predictor()` (`finetune.py`) always fits with a
  non-empty `known_covariates_names` (calendar features like `hour_of_day`
  are always present), so AutoGluon's `predict()` unconditionally requires
  future covariate values for the full horizon. But `_build_context()`'s
  `future_df` — sourced from the feature store — is always empty at the
  real production default (`as_of=None`, i.e. "forecast from today
  forward"), because no stage in the pipeline (`merge_pipeline.py`,
  `feature_engineering.py`, `run_pipeline.sh`) ever appends forward-looking
  placeholder rows for the actual forecast horizon; `merge_pipeline.py`'s
  `build_feature_store()` grid is built only from `transit_df`'s own
  *observed* timestamps. So the real forward-forecast case (the nightly
  job's actual purpose) hits AutoGluon's `ValueError: known_covariates ...
  should be provided at prediction time`, unconditionally. Backtests
  (`benchmarks.py`, `ablation.py`) never caught this because they always
  pass `as_of=val_end`, a mid-dataset cutoff where "future" rows are
  actually already-recorded historical months, not the true
  unobserved-future case. This needs a design decision, not a mechanical
  fix: either (a) generate deterministic future covariate rows for the
  horizon (calendar features are trivially computable; weather/event
  covariates would need a real forecast/schedule source — `fetch_weather_openmeteo.py`
  already fetches a forecast window, so this may be more tractable than it
  sounds), or (b) have `_finetuned_forecast()` detect `future_df.empty` and
  fall back to zero-shot with a clear warning rather than calling AutoGluon
  with `known_covariates=None`. Flagging for the project owner rather than
  guessing at the right tradeoff.
