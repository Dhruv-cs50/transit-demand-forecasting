## Correction to prior findings

Every prior daily log back to 2026-06-30 has flagged `.dt.tz_localize(None)`
calls on tz-aware Series as a crash bug ("TypeError in pandas ≥ 0.24"). **This
was verified today and does not reproduce** — in pandas 3.0.3 (and per the
documented `tz_localize` semantics), calling `tz_localize(None)` is safe on
*both* tz-naive and tz-aware Series/Timestamps; it's the documented way to
strip tz info without shifting the wall-clock time:

```
>>> pd.Series(pd.to_datetime(["2024-01-01"])).dt.tz_localize(None)   # naive input
0   2024-01-01
>>> pd.Series(pd.to_datetime(["2024-01-01"])).dt.tz_localize("UTC").dt.tz_localize(None)  # aware input
0   2024-01-01
```

Both succeed. The actually-dangerous call is `tz_convert(None)` on a
**tz-naive** Series (that one really does raise `TypeError: Cannot convert
tz-naive timestamps, use tz_localize to localize`), and every `tz_convert(None)`
call currently in the codebase (`merge_pipeline.py:128/185/191`) is already
correctly guarded with a `if ...dt.tz is not None` check. No changes needed
there. Flagging this so the backlog cleanup above doesn't waste more cycles
re-fixing a bug that isn't real.
