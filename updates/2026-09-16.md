| 1 | `models/baselines/benchmarks.py` (`diebold_mariano_test`) | Logged 2026-09-15 as a known-but-unfixed NaN-propagation issue ("left alone to keep the diff focused"). Re-tested today and it's worse than that log characterized: `predict.py`'s `forecast()` can legitimately leave `p10/p50/p90` as `NaN` for a station whose model didn't return a matching quantile column, and ridership itself can have null rows. With no NaN guard, `d = e_a - e_b` picks up `NaN`, `scipy.stats.ttest_1samp` returns `NaN` `t_stat`/`p_value`, and `p_value < 0.05` against `NaN` is always `False` — but the `winner: model_b if (...) else model_a` fallthrough then reports `model_a` (the baseline) as the winner even when the challenger model was actually better, not merely a masked "not significant" flag. Verified with a repro: one `NaN` row in the challenger's `p50` made the function report the deliberately-worse model as `winner` instead of the correct one. This feeds the project's benchmark leaderboard and `diebold_mariano.csv`. Fixed by masking `NaN` rows out of `y_true`/`p50_a`/`p50_b` before the t-test, returning `{}` if fewer than 2 valid rows remain. | High |
| 2 | `machine_learning_files/zero_shot.py` (`evaluate_predictions`) | Reimplements MAE/RMSE/MAPE/WAPE independently of `evaluation/metrics.py` (which got the shared `_valid_mask()` NaN-guard fix on 2026-09-15) and had no NaN guard of its own. A single missing actual/prediction for one station-month silently poisoned all four metrics to `NaN` for that station's *entire* zero-shot evaluation, feeding `forecast_all_stations()`'s printed summary and the saved `zero_shot_metrics_*.parquet`. Fixed with the same NaN-exclusion pattern used in `evaluation/metrics.py`; returns `{}` if nothing valid remains. Verified with a repro matching the pre-existing `evaluation/metrics.py` test shape. | High |

Verified structurally (511.org/Ticketmaster proxy-blocked in this sandbox): confirmed `IndexError` pre-fix on `{"classifications": []}`, then an end-to-end repro with a monkeypatched client session containing one malformed + one normal event returned both rows correctly post-fix. | Medium |

## Considered but not changed

- `machine_learning_files/zero_shot.py::evaluate_predictions`'s `WAPE`
  denominator can still be `inf` if all valid actuals in a slice are exactly
  zero (post-NaN-fix, pre-existing edge case, extremely unlikely with real
  ridership data) — left alone.
- `zero_shot.py::run_zero_shot_forecast` builds `context_input`/`future_input`
  wide-format frames that are never actually used (the real predict call uses
  the separately-built `context_long`/`future_long`) — dead code, not
  incorrect behavior, stylistic and out of scope.
- `models/baselines/fetch_pems_roads.py`'s `congestion_level` bucketing
  (`pd.cut(..., include_lowest=True)`, right-inclusive) disagrees by one
  bucket with the separately-computed `is_congested`/`is_stop_n_go` booleans
  (strict `<`) only at exact integer boundary speeds (15/35 mph) — real
  5-minute sensor readings rarely land exactly on the boundary, and it only
  affects a display label vs. a flag, not training columns. Not fixed.
- `fetch_events.py`'s `avg_ticket_price` calc treats a `$0` max price as
  missing (falsy-zero exclusion) — would silently drop free/promotional
  events from the average; low real-world likelihood and the field isn't
  used as a model feature. Left alone.
- `Processing/feature_engineering.py`'s `_add_monthly_event_features()`
  docstring claims it buckets `is_playoff` the same way as
  `merge_pipeline.py`, but the function body never touches `is_playoff` —
  it's already correctly set upstream and passed through untouched, so the
  output is correct; just an imprecise docstring sentence. Too pedantic to
  spend diff budget on.
- `machine_learning_files/fetch_bart_od.py`'s top-level `YEAR_MONTH_FORMAT`
  dict is unused dead code (`build_url_candidates()` hardcodes its own
  patterns) — stylistic, out of scope.
- `models/baselines/prophet_baseline.py::run_prophet_all_stations`'s
  `tz_localize(None)` without a prior `tz_convert` — re-confirmed the
  feature store's `timestamp` column is naive-by-default throughout this
  pipeline (same unreachable-dead-code pattern adjudicated 2026-09-12 and
  2026-09-15 for this file), not a new live bug.
- `website/api-demo.html`/`machine_learning_files/api.py`'s Pydantic `Field(example=...)`
  usage is deprecated under pydantic ≥2 (pinned `2.7.0`) in favor of
  `examples=`/`json_schema_extra`, but only emits an import-time deprecation
  warning — no behavior change. Not fixed.
- Google Maps API key hardcoded in `website/transit-demo.html` — unverifiable
  in this sandbox (no outbound network to the Maps API); not newly
