# Daily Update — 2026-07-10

## Correcting the record on the tz_localize backlog notice

The 2026-07-01 log flagged `tz_localize(None)` calls throughout the codebase
(`evaluation/validators.py`, `scripts/export_website_data.py`,
`machine_learning_files/merge_pipeline.py`, `models/baselines/prophet_baseline.py`)
as an unfixed bug carried over from the pre-2026-06-30 PR backlog, claiming it
raises `TypeError` on a tz-aware Series. **This was verified false today**: in
this repo's actual pinned pandas range (`pandas>=2.1.0`, no upper bound —
installed 3.0.3), `Series.dt.tz_localize(None)` does not raise on either
tz-naive or tz-aware input; it simply strips the tz label while preserving the
wall-clock value. The remaining `tz_localize(None)` call sites (in
`scripts/export_website_data.py` and `evaluation/validators.py`) are correct
as written and were left untouched. The real bug was the opposite mistake —
see #1 below, which is a **regression introduced by the 2026-06-30 fix** that
"corrected" a working `tz_localize(None)` call into a `tz_convert(None)` call
based on that same false premise.

## Bugs fixed today

| # | File | Bug | Severity |
|---|------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`compute_event_features`, lines ~184–191) | The 2026-06-30 fix changed `.dt.tz_localize(None)` to `.dt.tz_convert(None)` on event timestamps already localized to `America/Los_Angeles`. `tz_convert(None)` converts to UTC *before* stripping the tz label, shifting the wall-clock value — e.g. a 11pm PST game on Jan 31 becomes 7am UTC Feb 1. Since `compute_event_features` only uses `_year`/`_month` (extracted after this conversion) to bucket games by month, any evening event in the last ~8 hours of a month got silently miscounted into the next month's `is_game_day` / `hours_to_event` / `is_sharks_game` / `is_playoff` features, while the naive base timestamps it's compared against (from BART OD monthly periods and LA-local weather data) were never UTC-shifted. Reverted both occurrences to `.dt.tz_localize(None)`, which preserves the LA wall-clock value that the rest of the naive-timestamp pipeline expects. | High |
| 2 | `models/baselines/scheduler.py` (`step_fetch_weather`, `step_fetch_events`, `step_validate`, `NightlyPipeline.run` — lines 98, 115, 128, 223) | All four import/subprocess paths pointed at directories that don't exist in this repo: `ingestion.fetch_weather_openmeteo`, `ingestion.fetch_events`, `processing.validators`, and `"processing/merge_pipeline.py"`. The real locations are `machine_learning_files/fetch_weather_openmeteo.py`, `machine_learning_files/fetch_events.py`, `evaluation/validators.py`, and `machine_learning_files/merge_pipeline.py`. Every step is wrapped in a broad `except Exception`, so instead of crashing, **all 5 nightly steps silently fail** every single run (weather fetch, events fetch, feature-store rebuild, validation, and — gated behind validation passing — the forecast itself never runs). This is the scheduler described in the module docstring as what "keeps the +34% vs typical card on your website accurate rather than stale," and as shipped it does nothing. Fixed all four paths. | Critical |
| 3 | `machine_learning_files/requirements.txt` (line 12) | Pinned `chronos-forecasting>=1.3.0`, but `models/chronos2/predict.py` imports `Chronos2Pipeline`, which was only added in `chronos-forecasting>=2.0`. With no upper bound, a fresh install today happens to resolve to a 2.x release, so this wasn't causing failures in practice — but it's misleading and would break under a pinned/cached older resolution. Bumped the floor to `>=2.0.0`. | Low |
