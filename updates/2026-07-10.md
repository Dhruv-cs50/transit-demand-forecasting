# Daily Update — 2026-07-10

## Correcting the record on the tz_localize backlog notice

The 2026-07-01 log flagged `tz_localize(None)` calls throughout the codebase
(`evaluation/validators.py`, `scripts/export_website_data.py`,
`machine_learning_files/merge_pipeline.py`, `models/baselines/prophet_baseline.py`)
as an unfixed bug carried over from the pre-2026-06-30 PR backlog, claiming it
raises `TypeError` on a tz-aware Series. **This was verified false today**: in
this repo's actual pinned pandas range (`pandas>=2.1.0`, no upper bound —
installed 3.0.3), `Series.dt.tz_localize(None)` does not raise on either
tz-naive or tz-aware input; it simply strips the tz label while preserving the
wall-clock value. The remaining `tz_localize(None)` call sites (in
`scripts/export_website_data.py` and `evaluation/validators.py`) are correct
as written and were left untouched. The real bug was the opposite mistake —
see #1 below, which is a **regression introduced by the 2026-06-30 fix** that
"corrected" a working `tz_localize(None)` call into a `tz_convert(None)` call
based on that same false premise.

## Bugs fixed today

| # | File | Bug | Severity |

| 1 | `machine_learning_files/merge_pipeline.py` (`compute_event_features`, lines ~184–191) | The 2026-06-30 fix changed `.dt.tz_localize(None)` to `.dt.tz_convert(None)` on event timestamps already localized to `America/Los_Angeles`. `tz_convert(None)` converts to UTC *before* stripping the tz label, shifting the wall-clock value — e.g. a 11pm PST game on Jan 31 becomes 7am UTC Feb 1. Since `compute_event_features` only uses `_year`/`_month` (extracted after this conversion) to bucket games by month, any evening event in the last ~8 hours of a month got silently miscounted into the next month's `is_game_day` / `hours_to_event` / `is_sharks_game` / `is_playoff` features, while the naive base timestamps it's compared against (from BART OD monthly periods and LA-local weather data) were never UTC-shifted. | 4 | `machine_learning_files/fetch_events.py` (`enrich_events`, line 250) | `df["is_playoff"] = df.get("game_type", ...) == "3"` compares the NHL API's integer `gameType` field (1/2/3, per the code's own comment) against the string `"3"`. | 5 | `models/chronos2/predict.py` (`ridership_lift`, lines ~436–441) | The "typical" ridership baseline that powers the website's "+34% vs typical" card filtered on `hour_of_day == now.hour` and `day_of_week == now.dayofweek`. But the feature store is **monthly** (`configs/model.yaml`: month-start timestamps), so `hour_of_day` is always `0` (the filter is a no-op) and `day_of_week` is just whichever weekday the 1st of that month happened to land on — an arbitrary ~1-in-7 filter unrelated to real seasonality. With only ~24–36 months of history this frequently matches zero rows, making `typical_median` `NaN` and silently propagating to a `NaN` `lift_pct` instead of a meaningful number. Changed the mask to filter on calendar month (`timestamp.dt.month == now.month`), which is the correct "typical" comparison at monthly granularity, and added an explicit `NaN`/non-positive guard before dividing instead of the previous `max(typical_median, 1)` (which doesn't actually guard against `NaN`, since `max(nan, 1) == nan` in Python). | High |
