## New bugs found and fixed today

Delegated two independent read-only audits: one over the least-audited
ingestion scripts (`fetch_events.py`, `fetch_bart_od.py`,
`fetch_511_transit.py`, `fetch_weather_openmeteo.py`,
`fetch_pems_roads.py`), one over the export/website pipeline
(`export_website_data.py`, `run_pipeline.sh`, `eda_complete.py`,
`website/*`). Each finding below was independently re-read against current
`main` before fixing.

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/fetch_events.py` (`TicketmasterClient.get_events_for_venue`) | When a Ticketmaster event's start time is still TBD, the API returns only `localDate` (no `dateTime`), and the code's `else` branch produced a tz-**naive** `Timestamp` while the `if "T" in dt_str` branch (confirmed times) and `NHLClient`'s Sharks-game rows all produce tz-**aware** LA timestamps. Concatenating both event sources and calling `pd.to_datetime()` on the mixed column in `enrich_events()` raises `ValueError: Cannot mix tz-aware with tz-naive values`, crashing `fetch_all()` the moment any TBD-time Ticketmaster event exists alongside any Sharks game in the same date range — a real, common Ticketmaster state, not a hypothetical one. Fixed by localizing the date-only branch to `"America/Los_Angeles"` too, so every row is uniformly tz-aware before concatenation. | High |
| 2 | `machine_learning_files/fetch_bart_od.py` (`download_month`) | The per-URL try/except only caught `requests.RequestException`. A candidate URL returning HTTP 200 with a non-Excel body (bart.gov serves soft-404 HTML landing pages on some retired URL patterns) makes `parse_bart_od_excel` raise (`ExcelFile` parse error, or its own `ValueError("No parseable sheets found...")`) — neither is a `RequestException`, so the exception propagated out of the per-month loop uncaught, killing the entire multi-year batch job and discarding every month already accumulated before the final save. Added a second except clause around the parse call so a bad response just falls through to the next candidate URL/month instead of aborting the run. | High |
| 3 | `machine_learning_files/fetch_511_transit.py` (`Fetch511Client.get_lines`) | Used the wrong top-level JSON wrapper key — `data.get("Content", ...)` (singular) instead of `"Contents"` (plural), which is what the 511 static-GTFS API actually returns (and what the sibling `get_stops()` two lines above correctly uses). Against a real API response, `get_lines()` would silently return an empty DataFrame. Not currently reachable — nothing in the repo calls `get_lines()` yet — but a live bug the moment it's wired up. Fixed to match `get_stops()`'s key. | Low (dead code today, real bug on first use) |
