| 3 | `scripts/run_pipeline.sh` vs. `Dockerfile` | The script hardcoded `PYTHON=".venv311/bin/python"`, but `Dockerfile` installs all pipeline dependencies straight into the image's system Python (no venv is ever created) — and the Dockerfile's own header comment tells users to run this exact script inside the built image (`docker run transit-pipeline bash scripts/run_pipeline.sh`). | 4 | `machine_learning_files/api.py` (`get_pipeline`, `/forecast`) | Any `/forecast` request with an explicit `as_of` unconditionally routes past the cached-parquet fast path into the live-Chronos slow path (`cached_files and as_of is None` gates the fast path). `Dockerfile.api` — the only Dockerfile actually deployed to Cloud Run — deliberately never installs `chronos-forecasting` ("uses cached parquet files only", per its own header comment), so `get_pipeline()`'s `from chronos import ChronosPipeline` raised a bare `ModuleNotFoundError`, caught by the endpoint's generic `except Exception` and turned into an opaque 500 with a confusing message. `as_of` is a documented, publicly-accepted request field, so this was reachable by any real caller who set it. Fixed: `get_pipeline()` now raises a `RuntimeError` with an actionable message when the import fails, and the `/forecast` handler maps `RuntimeError` to a `503` instead of falling through to the generic 500. | Medium |
| 5 | `models/chronos2/finetune.py` (post-training summary print) | `scores.get('WAPE', 'N/A'):.4f}` (and the same for `MASE`/`MAE`) defeats its own fallback — if a metric key is ever missing from AutoGluon's `evaluate()` output, `.get()` returns the string `'N/A'`, which then hits the `:.4f` format spec and raises `ValueError: Unknown format code 'f' for object of type 'str'` instead of printing "N/A" as intended. Latent (all four metrics are expected back under normal `TimeSeriesPredictor.evaluate(metrics=[...])` usage) but a genuine correctness bug in the fallback itself. Fixed with an explicit `_fmt()` helper that checks for `None` before formatting. | Low |
| 6 | `transit_eda/notebooks/eda_complete.ipynb` (setup cell) | Hardcoded `os.chdir('/Users/dhruvshah/Desktop/transit-demand-forecasting')` — an absolute path that only exists on the original author's machine. Running the notebook top-to-bottom anywhere else, including this repo checkout, raised `FileNotFoundError` on the very first executable cell, so none of the notebook's 10 diagnostic plots could ever run. Reproduced the exact crash before fixing. Fixed by walking up from the current working directory to find the repo root (identified by `README.md` + `configs/model.yaml` both existing there), matching the portable pattern the sibling `eda_complete.py` script already uses (`Path(__file__).resolve().parents[1]`) — a notebook has no `__file__`, so this uses a cwd-search instead. (Caught and fixed an eager-default-argument bug of my own mid-fix: the first draft used `def _find_repo_root(start=Path.cwd())`, which captures `cwd` once at *function-definition* time rather than at each call — fine for this notebook's define-then-immediately-call usage, but a footgun for any future refactor. Moved `Path.cwd()` inside the function body instead.) | High |
| 7 | `transit_eda/notebooks/eda_complete.py` (BART loading section) | When none of the four hardcoded raw-data folders (`transit_eda/data/bart/<year>/...`) contain `.xlsx` files — true in this repo checkout, since no fetcher populates that tree (`fetch_bart_od.py` writes `.parquet` to a different path, `data/raw/transit/bart/`) — `pd.concat(bart_parts, ignore_index=True)` raised the opaque `ValueError: No objects to concatenate` after silently printing "⚠ No data loaded" four times.
