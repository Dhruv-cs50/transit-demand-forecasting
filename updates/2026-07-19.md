## Known issues logged (not fixed today)

- **`horizon_hours` silently ignored on the live-inference fallback path** —
  `machine_learning_files/api.py`'s `_run_forecast` and
  `models/chronos2/predict.py`'s `Predictor.forecast()` both compute
  `prediction_length`/`horizon_steps` from `cfg["data"]["forecast_horizon_steps"]`
  first (always `6` in `configs/model.yaml`), so the `if horizon_steps is
  None:` branch that would actually use the caller-supplied `horizon_hours`
  never runs — the live path always returns a fixed 6-step forecast
  regardless of what's requested. This is externally observable: `api.py`'s
  cached fast path *does* honor `horizon_hours` (`station_cache.head(horizon_hours)`),
  so a cache-empty request silently returns a different-length response
  than a cache-hit request for the same call. **Not mechanically fixed
  today** — `configs/model.yaml` has no `forecast_horizon_hours` key at all
  (only `forecast_horizon_steps`) and the pipeline's real granularity is
  monthly, so "hours" is not a well-defined unit to convert from here;
  naively honoring a `horizon_hours=24` default (the API's Pydantic field
  default) against a monthly cadence would silently drop most default
  requests to a 0-or-1-month forecast, a worse regression than today's
  "always 6 months." This looks like leftover drift from an earlier
  hourly-granularity design (see `models/chronos2/predict.py`'s
  `steps_per_hour`/30-day-month-approximation fallback code, which is
  correspondingly dead for the same reason) rather than a simple
  one-line fix — flagging for a product decision on what the parameter
  should mean at monthly cadence (rename to `horizon_months`? drop the
  override entirely and always use the config?) rather than guessing.
