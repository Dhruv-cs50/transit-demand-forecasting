## Bugs fixed today

**Reapplied from #43/#44 (independently re-verified against current `main`
before applying — each "before" snippet grep-checked to match exactly):**

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/fetch_events.py` (`get_all_venues`) | Ticketmaster events with a still-TBD start time (`dates.start` has only `localDate`, no `dateTime`) produced a tz-**naive** timestamp via `pd.to_datetime(dt_str)`, while confirmed-time events and every NHL/Sharks row are tz-**aware** (`America/Los_Angeles`). Concatenating both sources and calling `pd.to_datetime()` in `enrich_events()` raises `ValueError: Cannot mix tz-aware with tz-naive values` — a real, common Ticketmaster response state, not hypothetical. Fixed by localizing the date-only branch to `America/Los_Angeles` too. | High |
| 2 | `machine_learning_files/fetch_bart_od.py` (`download_month`) | Only wrapped the HTTP request in `except requests.RequestException`; an HTTP-200 response with a non-Excel body (a bart.gov soft-404 HTML page) let `parse_bart_od_excel`'s exception propagate straight out of the per-URL loop, killing the entire multi-year batch job on one bad month instead of just skipping that URL and trying the next candidate. Added a second `try`/`except` around the parse call so a bad body just falls through to the next candidate URL. | High |
| 3 | `machine_learning_files/fetch_511_transit.py` (`get_lines`) | Read the wrong top-level JSON key — `"Content"` instead of `"Contents"` (the sibling `get_stops()` two methods up correctly uses `"Contents"`). Silently returned an empty DataFrame against a real 511 API response. Currently dead code (nothing calls `get_lines()` yet), but a live bug the moment it's wired up. Fixed the key. | Low (dead today) |
| 4 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`) | The boolean `is_raining` column was aggregated with `"mean"` during the monthly weather rollup, same as the continuous columns beside it — turning a bool into a fraction (e.g. `0.23`) instead of using mode like its categorical sibling `weather_code` (already fixed for this same reason in an earlier audit). Every downstream `== True` / `== False` comparison on `is_raining` (`evaluation/metrics.py`, `Processing/ablation.py`, `models/baselines/benchmarks.py`'s rainy/clear-day breakdown) silently matched almost nothing, quietly emptying that diagnostic. Fixed to aggregate with the same mode logic as `weather_code`. | High |
| 5 | `machine_learning_files/zero_shot.py` (`main`, `--as-of` handling) | Same tz-strip-without-convert bug already fixed in `api.py`/`predict.py`/`models/chronos2/predict.py` was still present here: when the feature store is tz-naive but a user passes a tz-aware `--as-of` with a non-LA offset, `as_of.tz_localize(None)` stripped the tz label directly instead of converting to LA wall-clock time first — silently shifting the forecast anchor by hours (e.g. `08:00 UTC` becomes `08:00 naive` instead of the correct `01:00`). Fixed with the same `tz_convert("America/Los_Angeles").tz_localize(None)` pattern used everywhere else. | Medium |

All five fixes were independently re-verified by reading the current code
