## Known issues logged (not fixed today — need a design/infra decision, not a one-line fix)

- **`models/chronos2/finetune.py` never actually fine-tunes Chronos.** The `hyperparameters` dict passed to `predictor.fit()` (lines ~270–288) has no `"Chronos"` entry — a comment says "Chronos requires CUDA — excluded." The script trains `SeasonalNaive`/`AutoETS`/`DeepAR`/`TemporalFusionTransformer` successfully and reports a leaderboard, but nothing described as "the fine-tuned Chronos-2 model" downstream is actually Chronos. This needs either a CUDA-capable training environment or the docstring/naming corrected to stop implying Chronos gets fine-tuned here — not something to silently patch.
- **`models/chronos2/finetune.py`: two hand-maintained "known future covariates" lists have drifted apart.** `_default_covariate_cols()`'s list includes 8 columns (`precip_in`, `weather_code`, `cloud_cover_pct`, `is_very_cold`, `is_very_hot`, `is_windy`, `temp_deviation`, `is_playoff`) that `_get_known_covariate_cols()`'s separate list omits, so AutoGluon silently treats real known-in-advance weather/event signals as past-only. Recommend deduplicating to a single source of truth rather than patching one list in isolation.
- **Systemic landmine, 5 files**: `models/baselines/arima.py`, `models/baselines/prophet_baseline.py`, `machine_learning_files/zero_shot.py` (2 sites), `models/chronos2/finetune.py`, `models/chronos2/predict.py` all have a copy-pasted fallback that reads a `cfg["data"]["forecast_horizon_hours"]` key that doesn't exist anywhere in `configs/model.yaml`, then calls `.nanos` on the monthly (`"MS"`) frequency offset, which raises `ValueError` for non-fixed frequencies. Currently unreachable because the config always sets `forecast_horizon_steps`/`prediction_length_steps`, but a guaranteed double-crash (`KeyError` then `ValueError`) the first time someone edits the config to rely on the fallback. The equivalent bug in `Processing/ablation.py` was already fixed on 2026-07-01 without touching these 5 copies. Recommend consolidating into one shared helper instead of fixing 5 more copies individually.
- **Documentation drift** (not code bugs, but actively misleading):
  - `README.md`'s `POST /forecast` example response includes fields (`station_name`, per-item `date`, top-level `source`) that don't exist in the real `ForecastResponse` model, and omits real fields (`horizon_hours`, `generated_at`).
  - `README.md` states Chronos defaults to `device: mps`; the shipped `configs/model.yaml` has `device: "cpu"`.
  - `docs/ARCHITECTURE.md` references nonexistent `fetch_weather.py` and `prophet.py` filenames (real: `fetch_weather_openmeteo.py`, `prophet_baseline.py`) and documents `GET /stations` as returning objects with `station_name` when it actually returns a flat list of ID strings plus a count.
