Grepped every `pd.read_parquet()` cache-read call site across the whole audited data-ingestion area: this was the only one still unguarded. Verified live: seeded a corrupt `pems_d4_2022_01_01.parquet` cache file — before the fix, `get_5min_data()` raised an uncaught `pyarrow.lib.ArrowInvalid` that aborted the whole multi-day range loop (later days never even attempted, mirroring the exact "corrupt file kills the remaining batch" failure mode fixed elsewhere in this file family); after the fix, the corrupt file is logged, deleted, and the day falls through to a re-download attempt instead. `PeMSClient`/`get_5min_data` has no callers anywhere else in the repo (only reachable via a manual, interactive-login-gated `--mode live` CLI run, matching the already-logged "not wired into the pipeline" status), so real and reproducible but not reachable in any automated/production flow today. | Low |
| 2 | `machine_learning_files/api.py` (`_run_forecast`) | The 2026-09-25 fix mapped an `as_of` string that makes `pd.Timestamp(as_of)` *raise* (e.g. `"not-a-real-date"`) to a clean 400 via a new `InvalidRequestError`. It didn't cover the case where the parse *succeeds but silently returns `NaT`* — which pandas does for `""`, `"NaT"`, and `"nan"` (confirmed live: all three parse to `NaT` with no exception, while `"not-a-real-date"` still correctly raises and is caught). A caller sending e.g. `{"station_id": "EMBR", "as_of": ""}` — a plausible real value under the endpoint's `as_of: Optional[str]` contract, e.g. from an empty form field — flowed straight through with `as_of = NaT`; every downstream `<= as_of` / `> as_of` comparison in `prepare_context()` is then all-False, producing a silently empty context/future window instead of a clean error, rather than the documented "Default: now" behavior or a 400. Verified live with the exact parsing logic copied out of the file: `''`, `'NaT'`, and `'nan'` now correctly raise `InvalidRequestError("Invalid as_of value NaT: as_of parsed to NaT: NaT")`, `'not-a-real-date'` still raises the pre-existing message unchanged, and a well-formed ISO string still parses through untouched. Fixed by checking `pd.isna(as_of)` immediately after the `pd.Timestamp()` call and routing it through the same `ValueError → InvalidRequestError → 400` path as the unparseable-string case. Same masking caveat as the 09-25 fix it sits next to: invisible in the production Cloud Run deployment (no `chronos-forecasting` installed, so the request 503s before `as_of` is ever parsed), live on a local dev server — a real, documented usage path. | Low |
| 3 | `models/chronos2/predict.py` (`main`) | The standalone CLI's `--horizon` argparse default was `24`, not `None` — the only CLI in this exact code area (`arima.py`, `prophet_baseline.py`, `zero_shot.py` all use `default=None`) that doesn't let "no override" flow through to the config default. Harmless while `horizon_hours` was a dead no-op (pre-2026-09-18), but that fix made a non-`None` `horizon_hours` genuinely override the horizon for the naive/zero-shot backends — so running the module's own documented usage (`python models/chronos2/predict.py --station EMBR`, no `--horizon` flag) silently means "24 steps," 4x `configs/model.yaml`'s `forecast_horizon_steps: 6` default, and silently backend-dependent within a single command (6 steps with fine-tuned weights present, 24 without — the common case in this sandbox). Contradicts `forecast()`'s own docstring ("default from config"), which the CLI provided no way to actually invoke. Verified live: `forecast('EMBR', horizon_hours=None)` returns 6 rows (correct config default); `forecast('EMBR', horizon_hours=24)` — what every no-flag CLI invocation actually got — returns 24. Fixed by changing the default to `None` (confirmed via `argparse` that omitting `--horizon` now yields `args.horizon is None`, and `--horizon 24` still works explicitly) and updating the single-station branch's status print to show `"config default"` instead of crashing/mislabeling when `args.horizon` is `None`. | Medium |
