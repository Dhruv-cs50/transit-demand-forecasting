| 1 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | The 2026-09-21 fix made the sort *within* `hist_files` (and `forecast_files`) mtime-based, so a stale filename no longer beats a fresher one within its own group — but `frames = [historical_concat, forecast_file]` still concatenated historical rows ahead of forecast rows unconditionally, and the subsequent `drop_duplicates(subset=["timestamp","station"], keep="last")` let the *group order*, not actual recency, decide the winner for any overlapping `(timestamp, station)`. A forecast (predicted) value always beat a historical (observed) value for the same key, even when the historical file was written after the forecast file — reachable in production because `scheduler.py`'s nightly job only calls `fetch_forecast_all_stations()`, while the historical backfill (`fetch_historical_all_stations()`) is a separate, periodically-run process; re-running the backfill once Open-Meteo's archive API catches up on a day a stale, uncleaned forecast file already covered would silently overwrite the freshly-fetched observed weather with the old predicted value. Verified with a live repro: wrote a stale forecast file (`temp_f=55.0`), then 1.1s later a strictly-newer historical file (`temp_f=78.0`) for the same `(timestamp, station)`; before the fix `load_weather()` returned `55.0` (the stale forecast), after the fix it returns `78.0` (the fresher observed value). Fixed by tagging each group with its own source mtime (historical rows get the max mtime among `hist_files`; forecast rows get their file's own mtime) and sorting by that before `drop_duplicates(keep="last")`, so whichever group was actually written more recently wins regardless of concat order. | Medium |
| 2 | `models/baselines/benchmarks.py` (`compute_metrics`, `run_benchmarks`) | The module's own docstring promises the benchmark leaderboard includes "WAPE, MAE, RMSE, MAPE, **MASE**" — but the file never imported or called `mase()`, and `_metrics_row()` only ever produced `WAPE_%`/`MAE`/`RMSE`/`MAPE_%`/`sMAPE_%`/`Coverage_%`. `configs/model.yaml`'s `finetune.eval_metric` is literally `"MASE"` (the fine-tuned model's own training objective), so the head-to-head comparison script that's supposed to check whether the model beats SeasonalNaive/SARIMA/Prophet/zero-shot on that same objective never surfaced it at all — every prior benchmark run silently omitted the one metric the project optimizes for. Verified live: called `compute_metrics()` directly on a synthetic actuals/preds frame and confirmed the output dict had no MASE-related key. Fixed by threading an optional `train_df` param through `compute_metrics()` (mirroring `evaluation/metrics.py::_compute()`'s own contract: infer the seasonal period via the already-shared `_infer_seasonal_period()`, group the seasonal-naive scale by `station_id` via `mase()`'s existing `ids` param) and passing `run_benchmarks()`'s existing `train_df` into all five `compute_metrics()` call sites (SeasonalNaive, SARIMA, Prophet, zero-shot, fine-tuned). MASE is only added to a row when a usable `train_df` is supplied, so no call site regresses. Verified live: same repro now returns a `MASE` key (`0.2233` on synthetic data with a known model/naive-baseline ratio); confirmed omitting `train_df` reproduces the old no-MASE output exactly. | Low |
| 3 | `README.md`, `docs/ARCHITECTURE.md`, `machine_learning_files/README.md` | All three docs described the deployed Cloud Run API as if a cache miss actively runs live Chronos-2 inference today ("Cache miss triggers live Chronos-2 inference" / "cached parquet lookup → live Chronos inference fallback" / etc.) — but the production `Dockerfile.api` image (the one `cloudbuild.yaml` builds and `README.md`'s own "Docker Containers" section labels "used in production") never installs `chronos-forecasting`; `machine_learning_files/api.py::get_pipeline()` catches that `ImportError` and re-raises `RuntimeError("Live Chronos-2 inference is unavailable in this deployment...")`, which the `/forecast` handler maps to `503` — a fix already landed 2026-08-18 for exactly this reason. So on the real deployed service, any request falling through to the slow path always `503`s; live inference only happens on a local dev server started from `machine_learning_files/requirements.txt` (which does pin `chronos-forecasting`). Verified by cross-checking `Dockerfile.api`'s pinned pip list (no `chronos-forecasting`/`autogluon`) against `requirements.txt`'s (has it) and `api.py`'s `ImportError → RuntimeError → 503` path. Fixed all three doc references to state the production `503`-on-cache-miss behavior and scope the live-inference claim to a local dev server. Doc-only; no behavior change (the runtime already handles this correctly). | Low |
