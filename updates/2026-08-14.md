## Bugs fixed today

Three independent parallel audits, each scoped to a different subsystem
(data ingestion/feature pipeline, modeling/evaluation, API/website/config),
each given the prior two days' fix lists and "verified clean" lists up
front to avoid re-reporting known items. All 5 findings below were
independently re-verified against the actual current file contents before
fixing, and every touched Python file re-checked with `python3 -m
py_compile` after.

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`load_transit`) | BART OD Excel workbooks include a "Total Trips" sheet alongside the "Weekday"/"Saturday"/"Sunday" sheets (confirmed against `transit_eda/notebooks/eda_complete.py`'s own `sheet_map`, which explicitly excludes a "Total Trips (OD)" sheet before aggregating). `fetch_bart_od.py`'s `parse_bart_od_excel` tags every sheet as its own `day_type` with no exclusion, so `load_transit()`'s `groupby(...)["riders"].sum()` summed the Weekday+Saturday+Sunday sheets *and* the sheet that is already their monthly total — roughly doubling every station-month's ridership target. Same double-counting failure class as the 2026-08-12 glob-collision bug, different mechanism, and the same bug PR #55 (2026-07-29) already fixed once before it fell out of the branch lineage. Fixed by filtering out rows whose `day_type` contains "total" (case-insensitive) before the groupby-sum. | High |
| 2 | `Processing/ablation.py` (`run_inference_with_config`) | The quantile-column rename unconditionally mapped `"mean"` → `"p50"`, making the subsequent `"0.5"`-quantile fallback dead code — AutoGluon's `predict()` output always carries a `"mean"` column alongside the configured quantile columns, so every ablation config's `p50` silently used the point-forecast mean instead of the true median, feeding wrong values into `eval_on_slices`'s WAPE/MAE. Same bug class already fixed in `models/chronos2/predict.py` (2026-08-13) and `machine_learning_files/api.py` (today, #3) but present here as a third independent copy. Fixed to only fall back to `"mean"` when no `"0.5"`-named column exists. | Medium-High |
| 3 | `machine_learning_files/api.py` (`_run_forecast`, live-Chronos slow path) | `q_cols["p50"]` was selected via `next((c for c in pred_df.columns if "0.5" in str(c) or c == "mean"), None)` — an unordered OR that returns whichever column happens to appear first in `pred_df.columns`, not necessarily the true median column. `predict_df()` output carries both `"mean"` and `"0.5"` simultaneously, so this silently substituted the mean forecast for the median whenever `as_of` is explicitly set (backtest requests) or no cached forecast parquet exists — both real, reachable request paths. The file's own fast (cached) path a few lines above already only matches `"0.5"` with no fallback, exposing the inconsistency. Fixed to check for an actual `"0.5"` column first, falling back to `"mean"` only if none is found. | Medium |
| 4 | `machine_learning_files/merge_pipeline.py` (`make_splits`'s `_ts` helper) | For a tz-aware boundary input, used `tz_convert(None)`, which shifts to UTC before stripping the tz label — the same wrong-month/wrong-boundary hazard already fixed via `tz_localize(None)` a few lines above in `compute_event_features` in the same file. Currently unreachable (`train_end`/`val_end` are always naive date strings from `configs/model.yaml`), but fixed defensively for consistency with the already-corrected pattern in the same file. | Low (latent) |
| 5 | `models/chronos2/predict.py` (`Predictor.ridership_lift`) | `hour = int(future_row.iloc[0].get("game_start_hour", 19))` crashes with `ValueError: cannot convert float NaN to integer` whenever `is_sharks_game_window` is `True` but `game_start_hour` is `NaN` for that row — a real, reachable data gap: `merge_pipeline.py`'s own docstring documents `game_start_hour` as "NaN if no game," and its monthly aggregation can independently emit `NaN` even when `is_sharks_game_window` is `True` (unknown/TBD start times from the NHL/Ticketmaster feed). This function powers the website's "+34% vs typical · Sharks home game" card, so this crashes a live-demo forecast path, not just an offline script. Fixed by guarding with `pd.notna()` before the `int()` cast, falling back to the existing default of 19. | Medium |

## Known issues logged (not fixed today)

- The backlog-consistency problem remains the project's biggest actual
  risk — 63 open PRs, 29 days since the last merge, and now a concrete,
  repeated case (bug #1 above) of a previously-fixed bug resurfacing
  because its fix never made it into `main`. See "Backlog status" above.
- `predict.py::forecast()`'s `horizon_hours` argument (from the CLI
  `--horizon` flag and `scheduler.py`'s `horizon_hours=24`) is effectively
  ignored whenever `cfg["data"]["forecast_horizon_steps"]` is set (always
  true today) — consistent with the same step-based-config-wins pattern
  used throughout `arima.py`/`prophet_baseline.py`/`zero_shot.py`.
  Considered fixing the priority order but did not: doing so would make the
  already-known, deliberately-unfixed inverted `steps_per_hour` else-branch
  formula (see below) reachable, which is worse. Flagged as a candidate for
  a future look, not fixed today.
- `predict.py`'s `_naive_forecast` and `benchmarks.py`'s
  `seasonal_naive_forecast` both still have an inverted `steps_per_hour`
  formula in their else-branch (would `int()`-truncate to 0 for sub-hourly
  frequency), but `resample_freq` is hardcoded `"MS"` in
  `configs/model.yaml`, so this branch remains provably unreachable today.
  Re-confirmed, unchanged from prior logs.
- `ridership_lift`'s `is_raining` check reads a monthly-mean rain fraction
  as a truthy value rather than a real boolean, which can misfire on very
  light rain fractions — a soft precision issue, not a crash. Its root
  cause is in `merge_pipeline.py`'s monthly aggregation, outside today's
  finding's scope; flagged for a future pass.
- `configs/model.yaml` still has no `forecast_horizon_hours`/
  `context_length_hours` keys; the fallback call sites that reference them
  remain unreachable today because the step-based keys are always
  populated. Re-confirmed today, unchanged from prior logs.
- `models/chronos2/finetune.py`'s fine-tuning path and `predict.py`'s
  zero-shot fallback path remain unexercised end-to-end (no GPU packages or
  model weights available in this sandbox), consistent with every prior
  log.
