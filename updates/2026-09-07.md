| 1 | `Processing/feature_engineering.py` (`main`), `models/chronos2/finetune.py` (`load_train_val`) | The production fine-tuning path silently trains on the **wrong, pre-enrichment data**. `finetune.py`'s `load_train_val()` reads `data/processed/splits/{train,val}.parquet`, which are written *only* by `merge_pipeline.py`'s `make_splits()` — called from the raw, unenriched feature store (`scripts/run_pipeline.sh` step 1). `Processing/feature_engineering.py` (step 1.5) writes `feature_store_enriched.parquet` but never regenerated the splits, so no matter how many times the documented pipeline is run, `finetune.py` permanently trains on the raw schema. Diffed `finetune.py`'s own `KNOWN_FUTURE_COLS` (50 entries) against `merge_pipeline.py`'s documented raw-store schema: 30 of 50 are absent from the raw split and silently dropped by `_default_covariate_cols()`'s presence filter before ever reaching AutoGluon, along with all 12 `past_only` lag/rolling-stat features. Critically, the raw split only has the coarse `is_sharks_game`, not `is_sharks_game_window` (the fine-grained pre-game-window signal `KNOWN_FUTURE_COLS` actually references) — so **the shipped fine-tuned model is trained with zero working Sharks-game covariate**, despite that being this module's own stated #1 reason to fine-tune. Meanwhile `predict.py`'s `Predictor.get_feature_store()` prefers the enriched store at inference time — a real train/serve schema mismatch, not just a missing-feature gap. Fixed by having `feature_engineering.py`'s `main()` regenerate `data/processed/splits/{train,val,test}.parquet` from the enriched store (reusing `merge_pipeline.py`'s own `make_splits()` with the same `configs/model.yaml` boundaries) immediately after writing `feature_store_enriched.parquet`, so by the time `finetune.py` runs (pipeline step 5) the splits already reflect the full enriched schema. This also incidentally fixes bug #2 below at its root, since `evaluation/metrics.py`'s default `--actuals` (`splits/test.parquet`) will now carry the enriched, recomputed `is_raining` boolean instead of the raw fraction. Verified the import (`from machine_learning_files.merge_pipeline import load_configs, make_splits`) resolves and reads the correct `train_end`/`val_end`/`train_start` from config; all four touched files still `py_compile` clean. Could not exercise the full pipeline end-to-end in this sandbox (no real `data/raw/` inputs or AutoGluon install here, consistent with every prior log). | High |
| 2 | `evaluation/metrics.py` (`weather_day_metrics`, `main`) | Same bug class as `Processing/ablation.py`'s 2026-09-06 fix, but in a sibling module that fix didn't touch: `main()`'s backfill list (`diagnostic_cols = ["is_sharks_game_window", "precip_intensity"]`) never included `is_raining`, and its presence-only `missing` filter would have skipped it even if added — because `is_raining` is *already present* on a raw `splits/test.parquet`, just as the wrong type (`merge_pipeline.py`'s `build_feature_store()` writes it as a per-station-month **mean fraction**, not the boolean `feature_engineering.py` recomputes). `weather_day_metrics()`'s `merged["is_raining"] == True` then compares a continuous fraction against `1.0`, matching only a station-month that rained literally every hour — silently emptying the `"rainy"` key of this module's own docstring-advertised "Weather Breakdown" diagnostic on every default run. `"clear"` (`== 0.0`) happens to work more often, which is why casual output review wouldn't catch this. Verified with a synthetic repro built from the real schema: before the fix, a raw fraction column `[0.9, 0.0, 0.1]` never matches `== True`; after the fix, the enriched boolean `[True, False, False]` is correctly pulled in and `rainy` matches exactly the 1 true-rain row. | Medium-High |
