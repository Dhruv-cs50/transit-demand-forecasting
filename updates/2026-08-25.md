| 1 | `models/chronos2/predict.py` (`ridership_lift`) | The "reason" lookup (`is_sharks_game_window`/`is_raining`) filtered `station_df["timestamp"] > now`, where `now = forecast_df["timestamp"].iloc[0]` — the forecasted month's own timestamp. Since `forecast_df`'s timestamps originate from `_build_context`'s `future_df = station_df[station_df["timestamp"] > as_of]`, `now` exactly matches a real row in `station_df`. The strict `>` excluded that matching row and picked up `.iloc[0]` from the row *after* it, so the printed reason described the **next** month's Sharks-game/rain covariates instead of the forecasted month's own — e.g. a Sharks game in the forecasted month with no game the following month produced no reason at all, while a game only in the *following* month got misattributed to the current forecast. Verified against the current file: `_build_context` (`predict.py:201`) uses the identical `> as_of` pattern to build `future_df`, confirming `now` is an exact-match timestamp, not a gap. Only the explanatory `reason` string was affected — `lift_pct`/`forecast_p50` themselves were unaffected. Reachable via `predict.py`'s own CLI (`ridership_lift()` is called only from `main()`; not from `api.py` or `scheduler.py`). Fixed both occurrences (lines 531 and 543) to `>=`, so the lookup matches the forecasted month's own row. | Medium |
