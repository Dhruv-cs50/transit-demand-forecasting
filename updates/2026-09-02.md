## Bugs fixed today

Delegated three parallel, adversarial reads split by area (data ingestion +
feature engineering; modeling + evaluation; serving/website/config/docs),
each instructed to read the last 6 days of `updates/*.md` first and report
only genuinely new, currently-real findings. Found and independently
verified 5 new bugs (via traced code paths and synthetic repros) before
fixing them:

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/feature_engineering.py` (`add_event_features`, empty-events/empty-df early return) | `hours_to_next_event`/`hours_since_last_event` use `NaN` for "no event data available" everywhere else in this module — the main per-timestamp loop and `_add_monthly_event_features()` (the pipeline's actual production cadence) both agree on this — but the early-return guard hit when `events` is empty (e.g. a fresh pipeline run before `fetch_events.py` has produced any parquet, or a run with zero events retrieved) set these two columns to `0.0` instead, which reads as "an event is starting/ending this exact hour" for every single row. Verified with a direct repro: `add_event_features(df, pd.DataFrame())` produced `0.0` for both columns on every row before the fix, `NaN` after. Fixed by splitting the guard so only `event_proximity_score`/`nearest_event_attendance_tier` (legitimately `0` when no events) still default to `0.0`, while the two `hours_*` columns default to `NaN`. | Medium |
| 2 | `machine_learning_files/fetch_511_transit.py` (`get_stops`) | `float(s.get("Location", {}).get("Latitude", 0))` only substitutes the `0` default when the key is *absent* — a 511 SIRI stop with a pending/unassigned location (`"Latitude": null`) has the key present but `None`, so `.get(..., 0)` returns `None` and `float(None)` raises `TypeError`, killing the entire agency's stop list with no partial-success path (one malformed record silently drops the whole batch, caught only by the outer try/except in `fetch_stops_all_agencies()` and logged as a generic error). Same failure mode as the already-fixed Open-Meteo null-`weathercode` bug (2026-08-28), unguarded here. Reproduced with a stub payload containing one good stop and one with explicit `null` lat/lng. Fixed by reading the value first and checking `is not None` before the `float()` cast. | Medium |
| 3 | `models/chronos2/predict.py` (`Predictor._naive_forecast`) | `noise = np.random.normal(0, lag_val * 0.05)` passes a negative `scale` whenever the seasonal-naive lag pulled from the context window is negative, raising `ValueError: scale < 0` before the `max(0, ...)` clipping three lines later ever runs. This is the emergency fallback used when *both* the fine-tuned AutoGluon model and zero-shot Chronos fail to load — the "everything else is broken, this must always succeed" path — and negative ridership is a real, anticipated input class (`evaluation/validators.py` has a dedicated ERROR-level check for exactly this), while `Predictor.get_feature_store()` reads the parquet directly with no validation gate before this method sees it. Reproduced directly: `np.random.normal(0, -1.5)` raises `ValueError`. Fixed with `abs(lag_val) * 0.05`. Distinct from the 2026-08-29 fix to this same function (that one was a `period=0` `ZeroDivisionError` from sub-hourly frequencies). | Medium |
| 4 | `models/chronos2/predict.py` (`Predictor.ridership_lift`) | `lift_pct = (... ) / max(typical_median, 1)` doesn't guard against `typical_median` itself being `NaN` — happens whenever the "same calendar month, excluding game days" comparison set matches zero historical rows (plausible during hockey season at a catchment station with frequent home games). `max(nan, 1)` returns `nan` (Python's `max` compares with `>`, which is always `False` against `NaN`), and even the numerator (`forecast_p50 - NaN`) is `NaN` regardless. The caller's `lift.get("lift_pct") is not None` guard doesn't catch `NaN`, so the CLI/website "+34% vs typical" card rendered the literal string `"+nan%"`. Reproduced with an all-`False` `typical_mask`. Fixed by checking `pd.isna(typical_median)` up front and returning `lift_pct=None`/`typical_median=None` in that case, so the existing `is not None` guards work as intended and the display falls back to `"N/A"`. | Low-Medium |
| 5 | `models/chronos2/predict.py` (module docstring) | Claimed this module is "the single entry point called by ... `machine_learning_files/api.py` (FastAPI endpoint → Live demo on website)". Verified against current code: `api.py` has no import of `models.chronos2.predict` anywhere — it runs its own independent `_run_forecast()` that loads its own `ChronosPipeline` and calls `machine_learning_files/zero_shot.py`'s `prepare_context`/`run_zero_shot_forecast` directly, a separate zero-shot-only path that never touches the fine-tuned AutoGluon model or the `Predictor` class. `scheduler.py`'s half of the claim is correct (confirmed it does import and call `Predictor`). Fixed the docstring to drop the false claim and add an explicit note on which path actually serves live API requests. | Low |

All three touched Python files re-`py_compile`d to confirm no syntax errors; each fix independently repro'd (before/after) via direct calls to the affected function.
