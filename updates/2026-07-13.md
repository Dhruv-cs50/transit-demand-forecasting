## New bugs found today, not fixed (flagging for follow-up)

- **`machine_learning_files/merge_pipeline.py:277-300` — weather covariates
  are averaged across all 7 monitoring locations into one Bay-Area-wide
  number per month**, then joined to every station via `merge(..., on=["_year","_month"])`
  with no location key. El Cerrito and Berryessa (60 miles apart) get
  identical `precip_mm`/`is_raining`/`temp_f` for a given month, which
  defeats the point of having per-station weather at all. Fix needs a
  station→nearest-weather-location mapping before the join; deferred as a
  larger, separate change rather than guessing station-to-site distances
  in this pass.
- **`machine_learning_files/merge_pipeline.py:239-240` (`is_am_peak`,
  `is_pm_peak`) are permanently `False`** for the current monthly-cadence
  BART OD data — `add_calendar_features` derives them from `ts.dt.hour`,
  but every timestamp in the monthly feature store is midnight-of-month,
  so `hour_of_day` is always 0. Every consumer (`evaluation/metrics.py`'s
  hourly breakdown, `models/baselines/benchmarks.py`'s peak slices,
  `Processing/ablation.py`'s ablation slices) silently evaluates these as
  empty subsets instead of surfacing that the feature doesn't apply at
  this granularity. Not fixed today — needs a design decision (drop the
  columns at monthly cadence vs. compute a monthly-appropriate proxy)
  rather than a mechanical patch.
- `machine_learning_files/api.py:137`'s `horizon_hours` request parameter
  is applied as `station_cache.head(horizon_hours)` against monthly-cadence
  cached data (`prediction_length_steps: 6` in `configs/model.yaml`) — the
  field is documented "hours" but actually slices monthly rows, so
  `horizon_hours=1` silently returns 1 month labeled as if it were 1 hour.
  Low urgency (doesn't crash, just a misleading parameter name/semantics);
  flagging for the next pass.
