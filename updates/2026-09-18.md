| 1 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | Same bug class already fixed in `load_events()` (loading only the lexicographically-last file loses history), but at a call site `load_events()`'s fix didn't reach: `hist_files = sorted(...).glob("weather_all_stations_*.parquet")` then `pd.read_parquet(hist_files[-1])` loads only the single most-recent historical weather file instead of concatenating all of them. `fetch_weather_openmeteo.py`'s `fetch_historical_all_stations()` names its output `weather_all_stations_{start}_{end}.parquet`, embedding the CLI `--start`/`--end` args — so a later backfill re-run with a narrower or differently-dated range (e.g. the script's own documented usage example, `--start 2020-01-01 --end 2024-12-31`, run after an earlier `--start 2019-01-01` full backfill) sorts lexicographically *after* the fuller file and silently replaces it. Verified with a synthetic-data repro: a fuller 2019-01-01→2026-09-17 file plus a narrower 2020-01-01→2024-12-31 file (sorting last) produced 43,825 rows spanning only 2020–2024 under the old logic; the fixed logic (concat all historical files, dedupe on `(timestamp, station)` keeping the newest) produced 67,585 rows correctly spanning the full 2019–2026 range. | Medium-High |
| 2 | `models/chronos2/predict.py` (`Predictor.forecast`) | The caller-supplied `horizon_hours` argument was a complete no-op: `horizon_steps = cfg["data"].get("forecast_horizon_steps") or ...` is always truthy today (`configs/model.yaml` always sets it), so the `if horizon_steps is None:` branch — the only place `horizon_hours` was ever read — never runs. This silently defeated `predict.py`'s own `--horizon` CLI flag (any value produced the same fixed forecast length), its module docstring's usage example, and `scheduler.py`'s `step_forecast(horizon_hours=24)` call. Verified with a repro forcing the naive fallback path: `horizon_hours` values of 1, 24, 999, and 100000 all returned exactly 6 rows (the config default) before the fix. Fixed by having an explicit `horizon_hours` override the config-driven default for the naive/zero-shot backends (which can forecast an arbitrary length); the fine-tuned AutoGluon backend is structurally unable to honor an arbitrary horizon (`TimeSeriesPredictor.predict()` has no horizon argument — `prediction_length` is fixed at `fit()` time), so an explicit `horizon_hours` there is now logged and ignored rather than silently doing nothing. Matches the "hours-labeled, steps-valued" `--horizon` convention already used by `arima.py`/`prophet_baseline.py`/`zero_shot.py`'s CLIs. | Medium |
| 3 | `transit_eda/notebooks/eda_complete.py` (Sections 3.1, 4A, 4C) | Three separate aggregations sum `riders` across *all 12 months* of a year but label/print/chart the result as a **per-month** figure, inflating every reported number by ~12x: Section 3.1's `station_2023` (feeds the entire descriptive-stats table — "Mean exits/month", trimmed mean, IQR, top/bottom-5 tables — plus Section 5's skew/top-5%/top-10% narrative), Section 4A's `station_all_yrs`/`data_hist` histogram (x-axis labeled "Total Monthly Exits per Station"), and Section 4C's `od_matrix` heatmap (colorbar labeled "Avg Monthly Riders"). The file already has the *correct* two-step sum-within-month-then-mean-across-months pattern in `station_exits`/`station_annual` (lines 188–199) — each of these three sections re-derived its own aggregation and dropped that step. Verified with a synthetic constant-per-month repro: true per-month total of 200 reported as 2,400 (exactly 12x) under the old single-`.sum()` logic; fixed two-step aggregation reported the correct 200. Standalone EDA script (never feeds the model pipeline or live site, confirmed in prior audits), so no production impact — but it corrupts the notebook's own headline numeric output and two chart legends by an order of magnitude. Fixed all three sites to sum-within-month-then-mean-across-months, matching the file's own existing correct pattern. | Medium |
