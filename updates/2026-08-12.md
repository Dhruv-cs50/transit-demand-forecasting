# Daily Update — 2026-08-12

## ⚠️ The backlog has a worse problem than "nothing merges"

`main` is still current only through PR #42 (merged 2026-07-16, 27 days ago).
**64 open PRs** (#2–#68, excluding merged ones) sit unreviewed — every daily
audit since #42 has flagged this and it keeps growing (36 → 49 → 61 → 64).

But this pass found something more serious than an unreviewed queue. This
branch was built on top of **PR #68** (2026-08-11, the newest open PR) rather
than stale `main`, on the assumption that the chain of "reapply yesterday's
verified fixes" daily PRs is cumulative. **It isn't.** Ground-truth-checked
against PR #68's actual current file contents (not PR descriptions), the
following bugs are still present verbatim, despite prior PRs' own titles
explicitly claiming to have fixed the exact same issue:

| Bug (this update's # below) | Still broken in PR #68 despite being claimed fixed by |
|---|---|
| `predict.py` `_finetuned_forecast` missing `known_covariates` (#3) | PR #62 "Fix finetuned-forecast known_covariates omission" (2026-08-05) |
| `predict.py` `ridership_lift` day-of-week filter at monthly cadence (#4) | PR #48 (2026-07-22) **and** PR #65 (2026-08-08), both titled around "ridership_lift monthly-cadence baseline" |

| `merge_pipeline.py` `load_transit()` double-counting (#10) | PR #55 "BART … double-count" (2026-07-29), PR #61 "Fix BART OD double-counting" (2026-08-04) |

**Root cause, best guess:** each day's branch is built from `main` (still at
#42) plus a reapplication of only the *immediately preceding* day's PR, not
the full history. A fix that lands on day N but isn't picked up verbatim into
day N+1's reapplication step silently falls out of the lineage and never
comes back — even though the PR that introduced it is still sitting open and
its title still claims the fix. Over 26 days this has compounded: real,
previously-verified fixes are being repeatedly "found," "fixed," described in
a PR body, and then lost, at least 9 times confirmed in this pass alone (see
table above) — likely more across files this pass didn't re-check line by
line.

**This means the 64-PR backlog is not just "unreviewed" — most of it is not
even mutually consistent.** Merging the single most recent PR is *not*
equivalent to merging "the accumulated work of the last month," because the
accumulated work was never reliably retained in the first place.

**Recommend, in order of urgency:**
1. Merge this PR (or #68) into `main` now — breaking the cycle at all is
   better than another day of it continuing.
2. After merging, close the entire #2–#67 backlog as superseded rather than
   trying to reconcile them individually — several will contain small,
   real fixes never captured anywhere else, but auditing 66 stale branches
   by hand is far more expensive than re-running a thorough audit against a
   clean, merged `main` (which is what tomorrow's daily run would do anyway).
3. Fix the daily-audit automation itself: it should build each day's branch
   from the previous day's *branch tip*, not from `main`, or — better —
   someone should actually merge these PRs so the chain problem stops
   mattering.

| 5 | `machine_learning_files/api.py` (`_run_forecast`) | The pre-computed-parquet fast path returned cached forecasts for *any* request once a cache file existed, ignoring the caller's `as_of` entirely — a documented backtest request (`ForecastRequest.as_of`) silently got whatever anchor time the last cached batch run used.
