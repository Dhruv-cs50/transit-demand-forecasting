| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`, weather merge) | `has_match = base["weather_station"].notna()` followed by `matched[col].where(has_match, fallback[col])` only checks that a BART station *has a name mapping* into `STATION_TO_WEATHER_STATION` — not that `station_weather` actually has a row for that `(weather_station, year, month)`. `.where()` keeps the original value whenever the condition is `True`, even if that value is `NaN`. `fetch_weather_openmeteo.py`'s `fetch_historical_all_stations` fetches each of the 7 monitoring locations independently and tolerates per-station failure (logs and continues), so if one location's fetch ever fails, every BART station mapped to it gets `NaN` weather for the entire affected period instead of falling back to the regional average — silently defeating the fallback this code's own comment says it implements ("falling back to the regional average everywhere else"). Verified with a synthetic-data repro: old logic produced `[50.0, 55.0, nan, nan]` for a station whose weather source had no rows; fixed logic (`matched[col].fillna(fallback[col])`) produced `[50.0, 55.0, 60.0, 65.0]`, correctly substituting the regional average. | Medium-High |
| 2 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | One tz-stripping call site (`df["timestamp"].dt.tz_convert(None)`) was missed when every other tz-handling site in this file was fixed to the `tz_convert("America/Los_Angeles").tz_localize(None)` pattern (see the comment already in the file at the `_normalize_tz` helper explaining why `tz_convert(None)` alone shifts wall-clock time by converting to UTC before dropping the label — the same bug class fixed repeatedly since 2026-06-30). Currently dormant: `fetch_weather_openmeteo.py` always requests `"timezone": "America/Los_Angeles"` from Open-Meteo, which returns naive local-time strings, so `df["timestamp"].dt.tz` is `None` in practice today. Fixed for consistency and to prevent the bug from silently reappearing the moment weather data ever arrives tz-aware (a fetch-script change, or a manually supplied parquet). | Low-Medium (latent) |
| 3 | `evaluation/metrics.py` (`MetricsReport.__str__`) | `if self.mase is not None:` doesn't guard against `self.mase` being `float('nan')` — `mase()` can legitimately return `nan` (e.g. a multi-station `train_df` where one station's history is shorter than the seasonal period even though the concatenated length passes `_compute`'s aggregate-only length guard), and `nan < 1` evaluates to `False` in Python, so the printed report read `MASE: nan (trails naive)` — asserting the model is worse than seasonal-naive when the metric is actually undefined. `to_dict()`/CSV output were unaffected (`round(nan, 4)` correctly serializes as `NaN`); only the human-readable report text was wrong. Fixed to print `MASE: n/a (undefined — insufficient seasonal history)` when `mase` is `NaN`. Verified with both a `nan` and a real `0.8` `MetricsReport`. | Low |
