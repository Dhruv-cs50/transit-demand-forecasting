| 1 | `scripts/export_website_data.py` (`export_forecasts`) | The two `export_model_comparison()` code paths already guard MAE/MAPE/WAPE with `math.isfinite(...)` before writing to JSON (fixed 2026-08-13/14), but `export_forecasts()` — a third, separate `json.dump()` call in the same file that produces `website/data/forecasts.json` — had no such guard: `round(float(row[q10_col]), 0)` etc. ran unconditionally on quantile columns that can legitimately hold NaN (e.g. a station-month row the model couldn't produce a full-horizon prediction for). `json.dump()` then emits a bare `NaN` token, which is not valid JSON. Fixed with the same `math.isfinite()`-based helper pattern already used elsewhere in the file, applied to p10/p50/p90. | Medium |

## Known issues logged (not fixed today)

- The backlog-consistency problem remains the project's biggest actual
  risk — see "Backlog status" above. Fourth consecutive day flagging this.
- `transit_eda/notebooks/eda_complete.py`'s `load_bart_file_v1`/`v2` loaders
  assign the header row to `origin` and the first column to `destination` —
  the opposite row/column orientation from `machine_learning_files/fetch_bart_od.py`'s
  production parser, which treats rows as `origin` and columns as
  `destination`. This may be a real mislabeling, or it may correctly
  reflect that BART's raw OD workbook has a different orientation than the
  reformatted files the production fetcher downloads. No raw `.xlsx` source
  files are available in this sandbox to verify which is correct against
  real data, so this was **not** fixed — flagged for a future pass with
  real BART OD source files available.
- `models/chronos2/predict.py`'s `ridership_lift()` can compute
  `typical_median` as `NaN` when `typical_mask` matches zero historical
  rows (e.g. a station whose only data for a given calendar month was a
  game day, which `not_game_day` excludes entirely) — `max(NaN, 1)` returns
  `NaN` in Python, so `lift_pct` would be `NaN` in the returned dict. Not
  currently reachable from the live `/forecast` endpoint (only called from
  `predict.py`'s own CLI `main()`, which just prints the value), so this is
  a display quirk today, not a live-demo crash. Would be worth fixing if
  `ridership_lift()` is ever wired into `api.py`'s response.
- `website/sections.jsx`'s `Dataset` component displays hardcoded marketing
  copy ("Train (2019 + Jan–Dec 2022)") that doesn't match
  `configs/model.yaml`'s actual `train_start: 2021-01-01` (matches
  `docs/ARCHITECTURE.md`'s "Train Jan 2021 – Dec 2022" table instead). This
  is static website copy, not data-driven — a documentation/copy
  inconsistency, not a functional bug. Flagged, not fixed.
- `evaluation/validators.py`'s `EXPECTED_DTYPES` dict remains unused dead
  code (same class as `fetch_bart_od.py`'s already-logged `YEAR_MONTH_FORMAT`
  dead code) — no incorrect behavior, just unused. Re-confirmed, unchanged.
- `models/chronos2/finetune.py`'s fine-tuning path and `predict.py`'s
  zero-shot fallback path remain unexercised end-to-end (no GPU packages or
  model weights available in this sandbox), consistent with every prior
  log.
