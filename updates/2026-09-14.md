## Bugs fixed today

Delegated three parallel, adversarial full re-reads split by area (data

Found and fixed four real bugs today, three of them the same subtle root
cause recurring across independently-written functions:

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/feature_engineering.py` (`_add_monthly_event_features`) | `df["has_sharks"] = df["has_sharks"].fillna(False)` after a left `merge()` fills the `NaN` introduced for every `(year, month)` with no matching event row, but does **not** restore `bool` dtype — the column stays `object`, holding Python `True`/`False`/`NaN` mixed together (pandas upcasts a bool column to `object` the moment `NaN` enters it via a merge). `bool` is an `int` subclass in Python, so `~` on an `object`-dtype Series of Python bools silently does integer bitwise-invert (`~True == -2`, `~False == -1`) instead of logical negation. `nearest_event_attendance_tier`'s `is_sharks_game_window.astype(int)*2 + (is_any_event_day & ~is_sharks_game_window).astype(int)` therefore always added the truthy `~is_sharks_game_window` term regardless of its real value, so every Sharks-game month scored tier `3` instead of the documented major-event value of `2` (0=none/1=minor/2=major). Reachable on every real pipeline run: `_add_monthly_event_features()` is the branch `add_event_features()` takes whenever data is monthly-cadence — true for all real feature-store rows today — and the NHL API needs no key, so Sharks events are essentially always present in real event data. Fixed by restoring dtype: `.fillna(False).astype(bool)`. Verified live through the actual `build_features()` call: pre-fix a Sharks-game row returned `tier=3` with `is_sharks_game_window.dtype == object`; post-fix the same row returns `tier=2`, non-Sharks-event months return `1`, no-event months return `0`, dtype is real `bool`. | Medium-High |
| 2 | `Processing/feature_engineering.py` (`add_weather_features`) | Same root cause, different call site: `is_rain_onset` was computed as `is_raining & ~df.groupby(...)["is_raining"].transform(lambda x: x.shift(1).fillna(False))`. `x.shift(1)` on a bool Series introduces a leading `NaN` per group, upcasting to `object`; `.fillna(False)` alone doesn't restore `bool` dtype, so `~` again silently bitwise-inverts instead of negating, collapsing the whole expression to just `is_raining`'s own value. Every rainy period got flagged as an "onset," not only the first one after a dry spell — reachable on every real run (this line has no cadence guard, unlike the sub-daily `precip_*hr_sum` features a few lines above) whenever a station has two or more consecutive rainy periods, which is routine in Bay Area winter months. Fixed with `.transform(lambda x: x.shift(1).fillna(False).astype(bool))`. Verified with a dry→rain→rain-continues→dry→rain repro: pre-fix flagged the "rain continues" row as an onset (wrong); post-fix correctly produces `[False, True, False, False, True]`, onset only on true rain-starts. Grepped both touched files and the rest of the data-ingestion track for the same `~`/`fillna(False)` pattern; no other live instance found. | Medium |
| 3 | `Processing/ablation.py` (`offline_covariate_correlation`) | `numeric_cols = feature_store.select_dtypes(include=[np.number]).columns.tolist()` — pandas does not treat `bool` as a subtype of `np.number`, so every boolean covariate (`is_game_day`, `is_sharks_game_window`, `is_raining`, `is_weekend`, `is_holiday`, `is_am_peak`, `is_pm_peak`, `is_playoff`, `is_hub_station`, etc. — the majority of `COVARIATE_GROUPS["events"/"calendar"]`) was silently dropped from this diagnostic's correlation loop, with no error or warning that whole feature categories were missing from the printed "which covariates matter" report. `.corr()` on a bool column is a well-defined point-biserial correlation, so there was no reason to exclude it. Reachable on every run of `Processing/ablation.py main()` (both full and `--offline-only` mode), which writes `evaluation/outputs/covariate_correlations.csv` — the exact report this module exists to produce. Fixed with `select_dtypes(include=[np.number, "bool"])`. Verified with a repro: a synthetic boolean column engineered with a real +500 ridership lift was completely absent from the report before the fix and correctly appeared with `pearson=0.91` after. | Medium |
| 4 | `docs/ARCHITECTURE.md` (Mermaid system diagram + ASCII data-flow diagram), `README.md` (Cloud Data Storage table) | Both docs depicted `zero_shot.py` as downstream of `feature_engineering.py`, consuming `feature_store_enriched.parquet` like `finetune.py`/`arima.py`/`prophet_baseline.py`. The actual code (`zero_shot.py`'s `load_feature_store()`, `machine_learning_files/api.py`'s `get_feature_store()`) hardcodes the pre-enrichment `feature_store.parquet` and never touches the enriched file (`grep -rn "feature_store_enriched" machine_learning_files/api.py machine_learning_files/zero_shot.py` → zero matches) — meaning the live API's zero-shot inference path, both its cached-parquet and live-Chronos branches, skips all lag/rolling/cyclic engineered features, a materially different data-flow shape than documented. `machine_learning_files/README.md`'s own file table already had this right, which is what surfaced the inconsistency. Fixed by redrawing both diagrams so `zero_shot.py` branches directly off `feature_store.parquet` (bypassing enrichment) while `finetune.py`/`arima.py`/`prophet_baseline.py` remain downstream of `feature_store_enriched.parquet`, and rewriting the README table row to name both files and state which one the live API actually reads. Verified via `grep` cross-checks against `api.py`, `zero_shot.py`, `arima.py`, `prophet_baseline.py`, and `finetune.py`'s real file-loading code rather than trusting the prior docs. | Low (docs-only, but actively misleading about which artifact powers live inference) |

Bugs #1 and #2 share the exact same failure class: pandas upcasts a `bool`
column to `object` dtype the instant `NaN` enters it (via `shift()` or a

that `object`-dtype column silently does integer bitwise-invert instead of
logical negation — no exception, no warning, just a wrong answer. Both
tracks independently grepped their assigned files for the same
`~`/`fillna(False)`/`.any()` pattern afterward and found no further live
instances in scope.
