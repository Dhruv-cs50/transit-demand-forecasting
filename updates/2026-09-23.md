| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `models/baselines/fetch_pems_roads.py` (`fetch_pems_bay_dataset`) | The cached-read branch (`if cache.exists(): df = pd.read_csv(cache, ...)`) had no exception handling, while the download branch wrote the response body to the cache file (`cache.write_bytes(resp.content)`) *before* ever validating it parses as CSV — `resp.raise_for_status()` only checks the HTTP status code, not body content. If a download ever returns HTTP 200 with an empty/truncated/malformed body (a realistic failure given this sandbox's own documented proxy quirks), the bad bytes get written to `pems_bay_raw.csv`, the subsequent `pd.read_csv` fails, the `except` block catches it and falls back to synthetic data for *that* run — but never deletes the corrupt cache file. On the very next invocation, `cache.exists()` is `True`, so execution takes the unguarded read branch and crashes with an uncaught `pandas.errors.EmptyDataError` instead of self-healing back to synthetic data. Verified live: mocked `requests.get` to return an empty-body HTTP 200 response; run 1 fell back cleanly but left a corrupt cache file; before the fix, run 2 crashed on the cache-read path with `EmptyDataError`. Fixed by moving the cache-read into the same try/except as the download path, and deleting the unreadable cache file on failure before falling back to `_synthetic_road_data()`. Re-ran the repro after the fix: both run 1 and run 2 now fall back cleanly with no crash and no stale corrupt file left behind. | Medium |
| 2 | `models/baselines/arima.py` (`run_arima_all_stations`), `models/baselines/prophet_baseline.py` (`run_prophet_all_stations`) | Both functions built their training window as `train_df = df[df["timestamp"] <= cutoff]` — an upper bound only — silently ignoring `cfg["data"]["train_start"]` (`"2021-01-01"`, documented as "first continuous BART OD month available in current feature store"). `run_benchmarks()` in `benchmarks.py` *does* apply a `train_start`-filtered `train_df` for its own `SeasonalNaive` call, but never passed that bound to the SARIMA/Prophet calls, which instead received the full unfiltered `df` (which retains all history back to whatever `fetch_bart_od.py` was run with, e.g. 2019). Net effect: in the same benchmark run, SeasonalNaive and the AutoGluon fine-tuned model (which trains from a `train_start`-bounded parquet) trained on `[2021-01-01, val_end]`, while SARIMA and Prophet silently trained on `[earliest available, val_end]` — defeating the head-to-head model comparison this module exists for. Verified live: built a synthetic monthly feature store spanning 2019-01→2023-06 with `train_start: "2021-01-01"`, monkeypatched `fit_station` in both modules to capture the training window actually received — before the fix, both received `2019-01-01 → 2023-06-01` (54 rows); after the fix, both correctly receive `2021-01-01 → 2023-06-01` (30 rows), matching `run_benchmarks()`'s own `SeasonalNaive` window. Fixed by threading `cfg["data"].get("train_start")` through both functions and applying the same lower-bound filter `run_benchmarks()` already applies for itself, using each file's existing `_as_local_ts` tz-normalization helper. | Medium-High |
| 3 | `machine_learning_files/merge_pipeline.py` (module docstring "Schema:" block), `evaluation/validators.py` (`EXPECTED_DTYPES`) | Both files documented `ridership` as `float64`, but it's actually `int64` end-to-end: `fetch_bart_od.py` creates the source `riders` column via `pd.to_numeric(...).fillna(0).astype(int)` (NaN-free by construction), and `load_transit()`'s `.groupby(...)["riders"].sum()` over an all-int, NaN-free column never gets float-promoted; nothing downstream in `build_feature_store()` or `Processing/feature_engineering.py` ever reassigns or casts the column. Verified live with a synthetic per-month parquet matching `fetch_bart_od.py`'s real output schema fed through `load_transit()` directly: `ridership` dtype printed as `int64`. Cross-checked against `docs/ARCHITECTURE.md`'s independently-maintained Feature Store Schema table, which already correctly lists `ridership | int` — confirming this was a one-file staleness rather than genuine ambiguity, and the mirror-image of the `game_start_hour` docstring bug fixed in this same block on 2026-09-16. `validators.py`'s `EXPECTED_DTYPES["ridership"]` is currently dead/unwired (documented as such on 2026-09-22) so this caused no live validation failure today, but would have handed a false expectation to whoever wires it up next. Fixed both to `int64`. Doc/comment-only; no behavior change. | Low |
