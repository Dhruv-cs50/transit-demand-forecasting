Delegated three parallel, adversarial full re-reads split by area (data
ingestion + feature engineering; modeling + evaluation; serving/website/

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | Yesterday's (2026-09-24) fix tagged each *group* (`hist_files` vs `forecast_files`) with its own source mtime before `drop_duplicates(keep="last")`, so recency — not concat order — decides which value wins for an overlapping `(timestamp, station)` key. But the historical-group tagging used a single `max(mtime across ALL hist_files)` applied to every row in the group, regardless of which specific file that row actually came from. `hist_files` routinely contains more than one file in production (an original wide backfill plus later, narrower corrective re-fetches from repeated `fetch_historical_all_stations()` CLI runs, none of which get cleaned up), each written at a different time. A row from an *older* hist file silently borrowed the mtime of a completely unrelated, *newer* hist file in the same directory, so it could incorrectly "win" the dedup over a genuinely fresher forecast row for the same key — reintroducing yesterday's exact bug class one level down inside yesterday's own fix. Verified live: hist_file_A (oldest, `temp_f=70.0`) → forecast file 1.1s later (same key, genuinely fresher, `temp_f=55.0`) → hist_file_B 1.1s after that (unrelated station/date, present only to be the newest file in the hist group). Before this fix, `load_weather()` returned `70.0` (stale, borrowing hist_file_B's mtime); after, it returns `55.0` (the genuinely fresher forecast). Re-ran the original 2026-09-24 single-hist-file regression scenario to confirm no regression, and the full `build_feature_store()` pipeline end-to-end against synthetic data with no errors. Fixed by tagging each hist file individually with its own mtime before concatenating. | Medium |
| 2 | `models/chronos2/predict.py` (`Predictor`), `models/baselines/scheduler.py` (`step_forecast`) | `Predictor` is a process-wide singleton whose `get_feature_store()` caches the loaded feature-store DataFrame on `self._store` and never re-reads it once set. `scheduler.py`'s `--loop` deployment mode keeps one Python process alive across many nightly `NightlyPipeline.run()` iterations; steps 1–4 correctly rewrite `data/processed/feature_store_enriched.parquet` with fresh weather/events/ridership data each night, but step 6 (`step_forecast()`) calls `Predictor()`, which — being the same singleton — returns the instance from the very first run, with `_store`/`_predictor`/`_pipeline`/`_mode` already cached from night one. Every nightly forecast after the first silently reused night-one's stale snapshot forever, with no error, while every other pipeline stage kept refreshing normally on disk. Verified live: wrote a feature store, loaded it via `Predictor()`, overwrote the file on disk (simulating a second nightly run in the same process), and re-fetched — before the fix, `get_feature_store()` returned the stale first-run values; after adding `Predictor.reset_cache()` (clears `_store`/`_predictor`/`_pipeline`/`_mode`) and calling it at the top of `step_forecast()`, the second fetch correctly returns the fresh data. | Medium-High |
| 3 | `machine_learning_files/api.py` (`_run_forecast`, `/forecast` handler) | A malformed `as_of` string in a `POST /forecast` request (e.g. `"not-a-real-date"`) was silently misreported as a 404 "Not Found" instead of a 400 "Bad Request." `pd.Timestamp(as_of)` on an unparseable string raises pandas' `DateParseError`, a `ValueError` subclass; the handler's `except ValueError as e: raise HTTPException(status_code=404, ...)` branch — written for the distinct "Unknown station" case — catches it too, since `except ValueError` matches any subclass. Reachable whenever a caller supplies the API's documented `as_of` backtest-anchor field (accepted as a free-form, format-unvalidated `str`) with a bad value; masked in the production Cloud Run deployment by the already-known/logged chronos-not-installed 503 (which fires before the `as_of` parse), but live on a local dev server started from `machine_learning_files/requirements.txt` — a real, documented usage path. Verified live: confirmed `DateParseError`'s MRO includes `ValueError`; called the edited `_run_forecast()` directly (with `get_feature_store`/`get_pipeline` monkeypatched) and confirmed it now raises a distinct `InvalidRequestError` instead of leaking the bare `ValueError`, while a well-formed `as_of` and the "Unknown station" → 404 path are both unaffected. Fixed by adding an `InvalidRequestError` exception class and an `except InvalidRequestError → HTTPException(400)` branch ahead of the existing `except ValueError → 404` branch. | Low |
