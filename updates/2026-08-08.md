### New bugs found and fixed today

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `models/chronos2/predict.py` (`Predictor.ridership_lift`) | The "typical" baseline that powers the website's "+34% vs typical" card was computed by matching `hour_of_day == now.hour` and `day_of_week == now.dayofweek` — the same "hour/day-scale semantics never adapted for monthly cadence" bug class already fixed four times elsewhere in this repo (`is_am_peak`/`is_pm_peak`, event-proximity windows, `_infer_seasonal_period`), but never caught here. At the pipeline's real monthly cadence every timestamp is midnight-of-month, so the hour match is a no-op and the day-of-week match silently filters "typical" history down to whichever ~1/7 of months happened to start on the same weekday — a coincidence with zero seasonal meaning. No crash, just a silently wrong headline number computed from a noisy ~3–12 month sample instead of the full history. Fixed by guarding on `station_df["timestamp"].dt.hour.nunique() > 1` (mirroring `merge_pipeline.py`'s existing guard) and falling back to matching on `month` (same calendar month across prior years) when the data is monthly-cadence. | Medium |
| 2 | `evaluation/validators.py` (`validate_feature_store`) | The module docstring advertises catching "wrong dtypes," and an `EXPECTED_DTYPES` dict is defined for exactly that purpose, but no check function ever read it — `check_required_columns()` only checks column *presence*. This is the "data quality gate before any data reaches the model," called by `scheduler.py`'s nightly `step_validate()`, which gates whether the forecast step runs. If a schema-drift bug crept in upstream (e.g. `station_id` silently going numeric, or `timestamp` losing tz-awareness after a parquet round-trip — exactly the failure mode this project has hit repeatedly), the validator would report all-clear with dtype never inspected. Added `check_dtypes()`, wired into the `checks` list, comparing each `EXPECTED_DTYPES` entry against the actual column dtype (datetime-any-dtype check for `timestamp` to tolerate tz variants, exact match otherwise) and emitting an `ERROR`-level `ValidationResult` on mismatch. | Medium |
| 3 | `scripts/export_website_data.py` (`build_ridership_json`) | Dead `max_ridership = agg["avg_monthly_ridership"].quantile(0.95)` — computed but never referenced, and duplicates the same quantile `normalize_to_heat_scale()` already computes internally two lines later. No incorrect output, just vestigial. Removed. | Low |

All three fixes `python3 -m py_compile`-checked.
