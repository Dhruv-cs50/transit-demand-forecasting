Delegated three parallel, adversarial reads split by area (data ingestion +
feature engineering; modeling + evaluation; serving/website/config/docs),
each instructed to read the last 5-9 days of `updates/*.md` first and report
only genuinely new, currently-real findings. Found and verified one bug —
notably, one that *overturns a previous day's own claimed fix* rather than a
freshly-introduced defect:

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/ablation.py` (`run_ablation`) | The 2026-09-04 fix that backfills `is_sharks_game_window`/`is_game_day`/`is_raining`/`precip_intensity`/etc. from the enriched `feature_store` onto the raw `test_df` only pulls a column when it is **absent** from `test_df` (`missing = [c for c in diagnostic_cols if c not in test_df.columns and c in feature_store.columns]`). But `is_raining` is **not absent** — `machine_learning_files/merge_pipeline.py`'s `build_feature_store()` already writes it onto the raw store via `agg_kwargs`' `is_raining=("is_raining", "mean")`, a per-station-month **mean fraction** (0.0–1.0), and `make_splits()` carries that straight into `test.parquet`. Because it's already present, the presence-guard skips it, so it is never overwritten with `feature_engineering.py`'s recomputed boolean the 2026-09-04 fix intended — directly contradicting that day's log, which claimed the backfill "also fixes the rainy_day slice's own separate defect." `eval_on_slices()`'s `merged["is_raining"] == True` then compares a continuous fraction against `True` (i.e. `== 1.0`), matching only a month that rained literally every hour — the `rainy_day` diagnostic slice, one of this module's two headline breakdowns per its own docstring ("Rainy days — second most important signal"), silently returns zero rows on effectively every real run. `is_game_day` and the rest of `diagnostic_cols` don't have this problem — `is_raining` is the only column with a raw-vs-enriched semantic split, not just a presence gap. Verified with a synthetic repro built from the real schema: before the fix, the presence-guard's `missing` list excludes `is_raining` and the resulting `rainy_day` slice matches 0/3 rows even with 2 genuinely rainy months in the enriched data; after the fix (always force-overwriting `is_raining` from `feature_store` regardless of presence, alongside the existing absence-based backfill for the other columns), it correctly matches 2/3. | Medium-High |

## Considered but not changed

- `Processing/feature_engineering.py`'s `add_event_features()` docstring for
  `hours_to_next_event` says "negative = event already started," but
  `future_mask = delta_start > 0` structurally excludes any started event, so
  the column can only ever be `NaN` or positive — it can never be negative.
  No production consumer (`finetune.py`, `ablation.py`, `zero_shot.py`)
  inspects the sign, only `transit_eda/notebooks/eda_complete.ipynb` (a
  research notebook, not the production pipeline) assumes negative values
  exist. Real docstring/logic mismatch but no live behavioral effect — left
  as a documented discrepancy rather than widening today's diff.
- `models/baselines/fetch_pems_roads.py`'s `fetch_pems_bay_dataset()` cache-hit
  read path (`pd.read_csv(cache, ...)`) isn't wrapped in the same
  `try/except`-to-`_synthetic_road_data()` fallback the download path uses,
  so a stale/corrupted local cache file would crash instead of degrading
  gracefully. Plausible but low-priority: this script isn't invoked anywhere
  in `scripts/run_pipeline.sh` (standalone dev utility) and the trigger
  requires external interference with the cache file, since the
  write-then-read sequence in the download branch itself is safe. Not fixed
  today.
