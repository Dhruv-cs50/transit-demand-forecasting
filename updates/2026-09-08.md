| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `models/baselines/scheduler.py` (`NightlyPipeline.run()`) | The nightly cron job silently reverted 2026-09-07's fix every single night. Step 3 rebuilt the feature store by running only `machine_learning_files/merge_pipeline.py`, whose own `main()` unconditionally rewrites `data/processed/splits/{train,val,test}.parquet` **from the raw, pre-enrichment store** unless `--no-split` is passed — no flag was passed. It also never ran `Processing/feature_engineering.py`, so `feature_store_enriched.parquet` was never refreshed either, even though `predict.py`'s `Predictor.get_feature_store()` and `scheduler.py`'s own `step_validate()` both explicitly prefer that enriched file when present. Net effect: one night after any manual fix, the nightly job would (a) silently undo yesterday's train/serve schema fix by overwriting the splits with the raw schema again, and (b) keep the live "+34% vs typical" forecast card serving off a stale enriched snapshot while that night's freshly-fetched weather/events data sat merged into the raw store and never used. Verified by tracing `merge_pipeline.py`'s `parse_args()`/`main()` (confirmed `--no-split` exists and is the only way to skip the rewrite) and `Processing/feature_engineering.py`'s `main()` (confirmed it's the only place that regenerates the enriched store + re-derives the splits from it). Fixed by passing `--no-split` to the merge subprocess call and adding a new step right after it that runs `Processing/feature_engineering.py`, matching the ordering `scripts/run_pipeline.sh` already used. Renumbered the pipeline from 5 to 6 steps in logging, the module docstring, and added a `"features"` choice to `--step` for parity with the other steps. | High |
| 2 | `machine_learning_files/api.py` (`_run_forecast`, both the cached-parquet fast path and the live-Chronos slow path) | `max(0.0, float(row[q_col]))` silently turns a legitimately-missing quantile forecast into a fake "0 riders" prediction. Confirmed with a standalone repro: `max(0.0, float('nan'))` evaluates to `0.0` in Python, because NaN always loses float comparisons (`nan > 0.0` is `False`), so `max` returns its first argument. The cached parquet this reads (`models/chronos2/outputs/zero_shot_forecasts_*.parquet`) is the exact file `scripts/export_website_data.py`'s `export_forecasts()` reads, whose own comment already documents that quantile columns "can legitimately be NaN (e.g. a station-month row the model couldn't produce a full-horizon prediction for)" — a case that function was fixed to handle back on 2026-08-15 by emitting JSON `null`. `api.py`'s live `/forecast` endpoint hit the identical NaN case and emitted a plausible-looking `0.0` instead, which both frontend consumers (`api-demo.html`'s `fmtRiders`, `sections.jsx`'s live-fetch panel) would have rendered as an indistinguishable-from-real `"0"`. This exact pattern was flagged 2026-08-16/17 and dismissed with "no currently-reachable path to a NaN quantile was found" — reasoning contradicted by `export_website_data.py`'s own fix already being in the repo for the identical column at the time. Fixed with a `_clean_quantile()` helper that returns `None` (not a clamped `0.0`) for NaN/missing values, changed `QuantileForecast`'s `p10`/`p50`/`p90` fields to `Optional[float] = None` so FastAPI serializes it as JSON `null` (a raw Python `float('nan')` would have serialized as an invalid `NaN` token, breaking `response.json()` in the browser — checked this explicitly since simply returning NaN outright would have been a worse regression than the bug it fixed), and added the `f.p10 != null ? fmt(...) : '—'` guard to `sections.jsx`'s live-fetch panel (the one call site with no existing null-guard) so a `null` response renders "—" instead of the literal string `"NaN"`. Verified `_clean_quantile` against `nan`, `None`, `pd.NA`, a negative value, and a normal value. | Medium |
| 3 | `README.md`, `docs/DATA_PIPELINE.md` | Both docs' pipeline-steps sections still described 2026-09-07's structural fix incorrectly: `README.md`'s step 2 and `docs/DATA_PIPELINE.md`'s §3 said only "build `feature_store_enriched.parquet`," with no mention that this step (added 2026-09-07) also silently overwrites `data/processed/splits/{train,val,test}.parquet` from the enriched store — directly overwriting what step 1/§2 just wrote. A reader following either doc as written would reasonably (and now incorrectly) believe the splits were fixed after step 1/§2 and untouched afterward. Given this project has repeatedly shipped real bugs on exactly this raw-vs-enriched provenance question (bug #1 above being the latest), left the docs stale on it risked exactly the kind of confusion that causes those bugs. Fixed both to describe the actual current behavior. | Low (docs only) |
