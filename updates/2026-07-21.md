inference path — i.e. every place that calls the trained model, not the
zero-shot fallback:

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 10 | `models/chronos2/predict.py` (`Predictor._finetuned_forecast`) | Called `self._predictor.predict(ts_df, prediction_length=horizon_steps)`. `TimeSeriesPredictor.predict()` has no `prediction_length` parameter — the horizon is fixed once at construction time in `finetune.py::build_predictor()` (`TimeSeriesPredictor(..., prediction_length=prediction_length, known_covariates_names=known_cov_cols, ...)`). Passing an unrecognized keyword raises `TypeError`, crashing the entire fine-tuned forecast path — the code path taken by `predict.py`'s own CLI once fine-tuned weights exist, `models/baselines/scheduler.py`'s nightly forecast refresh, and `models/baselines/benchmarks.py`'s "AutoGluon ensemble" leaderboard row. Compounding this: the method's own `future_df` parameter (built by `_build_context` specifically to carry the weather-forecast/event-schedule rows known ahead of the forecast origin) was accepted but never referenced anywhere in the body — even after removing the bad kwarg, the predictor would still be missing the `known_covariates` it requires because `known_covariates_names` is non-empty. Fixed by dropping the invalid kwarg and building a `known_covariates` `TimeSeriesDataFrame` from `future_df` (renaming `station_id`→`item_id`, restricting to `horizon_steps` rows per station, keeping only the columns in `finetune.py`'s `KNOWN_FUTURE_COLS` — the same constant `finetune.py` uses to build `known_covariates_names`, so the two can't drift apart the way the pre-2026-07-16 covariate list did). | Critical |
| 11 | `Processing/ablation.py` (`run_inference_with_config`) | Same invalid `prediction_length=` kwarg as #10 (independent occurrence, would raise the identical `TypeError`). Also, independently: `feature_store` here is the *entire* enriched store (train+val+test, per `main()`'s `--feature-store` default), and the pre-fix code built `TimeSeriesDataFrame` from all of it. `predict()` forecasts starting *after the last timestamp of each item in `data`* — feeding it the whole store (which extends through the test period) meant every produced forecast landed on dates past the entire store's range, never overlapping `test_df`'s actual timestamps. `eval_on_slices()`'s inner join on `(timestamp, station_id)` would then be empty for every one of the 6 ablation configs, and `run_ablation()`'s blanket `except Exception` (or a silent empty-DataFrame join) would produce a report with no rows — with no warning that anything had gone wrong. Fixed by threading `test_df` into the function, splitting `ablated_df` at `test_df["timestamp"].min()` into a context window (passed as `data`) and the ablated test-period rows (passed as `known_covariates`, restricted to `KNOWN_FUTURE_COLS`) — mirroring the same fix pattern as #10 and how the predictor actually consumes covariates. Removed the now-dead `cfg` parameter and its unused `prediction_length` computation block, since the horizon is no longer computed here at all. | High |

Neither bug could be exercised end-to-end in this sandbox (no `autogluon`
package or fine-tuned model weights available); finding #10 was verified
by fetching AutoGluon's actual `predictor.py` source and confirming its
`predict()` signature is `predict(self, data, known_covariates=None,
model=None, use_cache=True, random_seed=123)` — no `prediction_length`,
and `known_covariates` is exactly the parameter both bugs needed and
lacked.
