| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`load_events`), `Processing/feature_engineering.py` (`main`) | `fetch_events.py`'s `fetch_all()` names its output `events_{start}_{end}.parquet` for **both** the one-time historical backfill (`docs/DATA_PIPELINE.md`'s documented setup step, `start=2019-01-01`) and the nightly incremental fetch (`scheduler.py`'s `step_fetch_events()`, `start=today`, `end=today+30d`). Both `load_events()` and `feature_engineering.py`'s `main()` picked "most recent by filename sort" (`files[-1]`) to decide which single file to load. Because filenames sort lexicographically and `today` (2026-xx-xx) always sorts after the fixed `2019-01-01` backfill start, **the very first nightly cron run permanently and irreversibly wins** — every subsequent pipeline rebuild reads only the ~30-day forward window and silently loses years of historical event data, with no error or row-count anomaly to notice. `compute_event_features()`/`_add_monthly_event_features()` then bucket every historical station-month against this narrow file, so every real past Sharks game gets `is_game_day=False`, `is_sharks_game=False`, `hours_to_event=0.0` — zeroing out this project's single most-marketed covariate (the Sharks-game/Diridon-VTA signal) across the entire training/val/test history, on every pipeline run after the first nightly execution. Distinct from and compounding the already-known "future covariates never generated" issue (that one affects the forward-forecast path only; this one corrupts the historical training signal). Weather doesn't share this defect — it uses two distinct filename prefixes for historical vs. nightly-forecast data, so its historical file is never at risk of being shadowed; events is unique in reusing one filename pattern for both. Verified with a live repro (synthetic historical + nightly parquet files under a real `data/raw/events/`-shaped directory, cleaned up after): `load_events()` loaded the nightly file only and `compute_event_features()` on a historical Sharks-game row returned `is_sharks_game=False`; re-run after the fix loaded and correctly attributed both games. Fixed by loading and concatenating **every** `events_*.parquet` file in both call sites, deduping on `(timestamp_start, venue, event_name)` (NHL uses `game_id`, Ticketmaster uses `event_id` — no single id column unifies both event sources, so the dedup key uses columns both share) — mirroring the historical/incremental merge pattern weather already uses correctly. | High |
| 2 | `Processing/ablation.py` (`run_inference_with_config`) | Unconditionally called `predictor.predict(ts_df)` with no `known_covariates` argument at all. `finetune.py`'s `build_predictor()` always fits with a non-empty `known_covariates_names` (calendar columns like `hour_of_day` are always present in the feature store), and confirmed against the real pinned `autogluon.timeseries` source (both the `>=1.1.0` floor and current `1.6.1`) that `TimeSeriesLearner._align_covariates_with_forecast_index()` unconditionally raises `ValueError: known_covariates ... should be provided at prediction time` whenever `known_covariates_names` is non-empty and `known_covariates=None` — on **every** call, for **every** ablation config. `run_ablation()`'s per-config `try/except` swallows this and logs `"Config {config_name} failed: ..."`, so the entire ablation study (this module's sole purpose) silently produces zero results whenever run against real fine-tuned weights — `main()` always prints "Ablation produced no results". Distinct from the already-fixed (2026-09-09) invalid-`prediction_length`-kwarg bug in the same function; this is a second, separate defect in the same `predict()` call. Fixed by mirroring `predict.py`'s `_finetuned_forecast()` pattern: slice the horizon's rows from `feature_store` (`timestamp > as_of`), apply the *same* ablation zeroing used for the historical context (so a config's zeroed covariate groups stay zeroed for the forecast window too, not just history — keeping the ablation methodology internally consistent), and build `known_covariates` from only the columns the predictor was actually fit to expect ahead of time (`finetune.py`'s `KNOWN_FUTURE_COLS`). Same "unexercised end-to-end" caveat as recent AutoGluon findings (no GPU/weights in this sandbox) — verified by source-level tracing against the real pinned library rather than a live run. | High |
| 3 | `machine_learning_files/zero_shot.py` (`run_zero_shot_forecast`) | `pipeline.predict_df(..., future_df=future_long, ...)` is always called with a `future_df` kwarg, but `configs/model.yaml` pins a Chronos-1 T5 checkpoint (`amazon/chronos-t5-small`) loaded via the base `ChronosPipeline` class (same class choice `predict.py`'s `_load_zeroshot` already documented as correct for this `model_id`, vs. the Chronos-2-only `Chronos2Pipeline`). Downloaded and inspected the actual published `chronos-forecasting` source across the project's full supported range: versions `1.3.0`–`1.5.3` (within the stated `>=1.3.0` requirements floor) have **no `predict_df` method at all** on this class (raises `AttributeError`, not caught by the existing `except TypeError:`); versions `2.1.0`–`2.3.2` (what an unpinned `pip install` resolves to today) do have `predict_df`, but its signature never accepts `future_df`/covariates for the base `ChronosPipeline` class — only `Chronos2Pipeline.predict_df()` does (its base-class docstring literally says "any covariates, if present, are ignored here"). So this call fails on every currently-realistic dependency resolution: it always falls back to univariate-only forecasting under the current unpinned range (contradicting the module's own docstring, "with weather and events as past/future covariates"), or crashes uncaught under the project's own stated floor version. Verified with a standalone repro using stub classes matching the real downloaded signatures for both ranges. Fixed by widening the fallback to `except (TypeError, AttributeError)` so the floor-version crash is caught like the newer-version case already was, and corrected the surrounding comment/log to state plainly that covariates are unavailable via this code path today rather than implying it's a versioning edge case. | Medium |
