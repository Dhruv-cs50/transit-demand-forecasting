## Bugs fixed today (reapplied from PR #49, independently re-verified against current `main`)

Reapplied as commit `2c390c4` (each "before" snippet matched current `main`
exactly, confirmed via `git apply --check`, then every edited Python file

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|

| 3 | `Processing/feature_engineering.py` (`add_weather_features`) | Inverted sort condition (`if is_monotonic_increasing: sort()`) ahead of rolling precipitation windows. | Medium |
| 4 | `Processing/feature_engineering.py` (`main`) + `machine_learning_files/merge_pipeline.py` | `make_splits()` ran before feature enrichment, so `splits/*.parquet` never carried event/weather diagnostic columns. Fixed by re-cutting splits from the enriched store. | High |
| 5 | `machine_learning_files/api.py` (`_run_forecast`) | Cached fast path ignored the caller's `as_of` parameter entirely. Fixed to only take the fast path when `as_of is None`. | High |
| 6 | `machine_learning_files/fetch_511_transit.py` (`get_lines`) | Read `"Content"` instead of the correct `"Contents"` top-level JSON key. | Low (dead today) |
| 7 | `machine_learning_files/fetch_bart_od.py` (`download_month`) | An HTTP-200 non-Excel body could kill the entire multi-year batch job on one bad month. Wrapped the parse call to fall through to the next candidate URL. | High |
| 8 | `machine_learning_files/fetch_events.py` (`get_events_for_venue`) | TBD-time Ticketmaster events produced a tz-naive timestamp while confirmed-time events are tz-aware, raising `ValueError` on concat. Localized the date-only branch too. | High |
| 9 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`) | Boolean `is_raining` aggregated with `"mean"` instead of mode, silently breaking downstream `==True/False` filters. | High |
| 10 | `machine_learning_files/zero_shot.py` (`main`) | Same tz-strip-without-convert bug fixed elsewhere in the codebase: `.tz_localize(None)` on a non-LA tz-aware timestamp kept the wrong wall-clock digits. Fixed with `tz_convert("America/Los_Angeles").tz_localize(None)`. | Medium |
| 11 | `models/chronos2/predict.py` (`_finetuned_forecast`) | Called `.predict(ts_df, prediction_length=horizon_steps)` — invalid kwarg — and never used the `future_df` known-future covariates it received. Fixed to build `known_covariates` and drop the bad kwarg. | Critical |
| 12 | `models/chronos2/predict.py` (`ridership_lift`) | "Typical for this hour/day-of-week" baseline was meaningless at monthly cadence (hour always 0), and could silently produce `NaN` lift with no matching rows. | 13 | `models/chronos2/predict.py` (`Predictor._ensure_loaded`) | When `force_mode` is passed, the method called the corresponding loader but ignored its return value and unconditionally set `self._mode = force_mode` regardless of whether the load actually succeeded — leaving `self._predictor`/`self._pipeline` as `None` while `forecast()` dispatched into the real-model path anyway, raising `AttributeError`. Fixed to only honor `force_mode` when the corresponding loader actually succeeded, else falls back to `"naive"` with a warning. | Medium |
| 14 | `website/charts.jsx`, `website/sections.jsx` | Both hardcoded the winning model as `'AutoETS (AutoGluon)'`, a string `benchmarks.py` has never emitted (`compute_metrics` uses `"AutoGluon_Ensemble"`) — the leaderboard never highlighted the winning row and printed the raw internal name to visitors. Fixed both to key on `'AutoGluon_Ensemble'`. | Medium |

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 15 | `machine_learning_files/merge_pipeline.py` (`load_weather`) | The nightly scheduler's weather-forecast step (`fetch_weather_openmeteo.fetch_forecast_all_stations`, invoked from `models/baselines/scheduler.py`'s `step_fetch_weather`) writes its 7-day-ahead forecast to `weather_forecast_<timestamp>.parquet`. `load_weather()` only ever globbed for `weather_all_stations_*.parquet` — a completely different filename pattern — so every forecast row fetched nightly was silently discarded and never reached the feature store. Every future-dated row's weather covariates (`is_raining`, `precip_mm`, `weather_code`, etc. — all listed in `finetune.py`'s `KNOWN_FUTURE_COLS`) stayed stale/missing no matter how often the nightly job ran, undermining the scheduler's own documented purpose for that step (keeping forecast-time weather covariates current). Verified via full-repo grep that nothing else reads `weather_forecast_*.parquet`. Fixed by having `load_weather()` also glob for `weather_forecast_*.parquet`, merge in the latest file, and de-duplicate on `(station, timestamp)` with archive rows taking priority. | High |
