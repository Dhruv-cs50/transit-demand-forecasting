# Daily Update — 2026-07-05

## Correction to a prior day's finding

The 2026-07-01 log listed `tz_localize(None)` on tz-aware Series as a still-broken
bug in `prophet_baseline.py` (3 sites), `export_website_data.py` (2 sites), and
`evaluation/validators.py` (1 site), inherited from a 2026-06-30 claim that this
"raises `TypeError` in pandas ≥ 0.24." Verified against the pinned dependency
(`pandas>=2.1.0`, tested on 3.0.3): `tz_localize(None)` does **not** raise on a
tz-aware or tz-naive Series — it's a documented no-op-safe way to drop the tz
label while preserving local wall-clock time. Those 6 sites are not bugs; no
changes needed there. This also means the 2026-06-30 "fix" that swapped
`tz_localize(None)` → `tz_convert(None)` in `merge_pipeline.py` was based on a
false premise — see bug #1 below, which is the real, verified issue it introduced.

## Bugs fixed today

| # | File | Bug | Severity |

| 1 | `machine_learning_files/merge_pipeline.py` (`compute_event_features`, `load_weather`) | The 2026-06-30 change from `tz_localize(None)` to `tz_convert(None)` shifts tz-aware timestamps to UTC *before* dropping the tz label, instead of preserving local wall-clock time. Since events/weather are then bucketed by `_year`/`_month`, a late-night local event near a month boundary gets miscounted into the wrong month. Reproduced: an NHL game at 11:00 PM PDT on Apr 30 became `2026-05-01 06:00` after `tz_convert(None)` — Chronos's `is_game_day`/`is_sharks_game`/game-count features would have counted it in May instead of April. Reverted both sites (plus the analogous `load_weather` site) to `tz_localize(None)`. Verified with a direct call to `compute_event_features()` — the game now correctly lands in April's row. | High |
| 2 | `models/baselines/scheduler.py` (`step_fetch_weather`, `step_fetch_events`, `step_validate`) | Three import paths pointed at modules that don't exist in this repo: `ingestion.fetch_weather_openmeteo`, `ingestion.fetch_events`, `processing.validators` (no `ingestion/` directory exists at all; the real `processing` package is capitalized `Processing/` and doesn't contain `validators.py` either — that lives in `evaluation/validators.py`). Each step wraps its body in a broad `except Exception`, so every nightly run silently logged "fetch failed" / "validation failed" and returned `False` without ever actually running — the nightly weather pull, events pull, and data-quality validation have likely never executed successfully. Fixed all three to their real locations: `machine_learning_files.fetch_weather_openmeteo`, `machine_learning_files.fetch_events`, `evaluation.validators`. Verified all three now import cleanly. | High |
| 3 | `models/chronos2/predict.py` (`_load_zeroshot`) | Loaded `model_id = "amazon/chronos-t5-small"` (a legacy T5-architecture Chronos-1 checkpoint, per `configs/model.yaml`) via `Chronos2Pipeline.from_pretrained`, which asserts the checkpoint's HF config has `chronos_config` set to a genuine Chronos-2 architecture and looks up `config.architectures[0]` in the `chronos.chronos2` namespace — a T5 checkpoint fails that lookup. `machine_learning_files/zero_shot.py` already loads this exact same `model_id` correctly via `ChronosPipeline`. Refines the 2026-07-01 log's diagnosis: `Chronos2Pipeline` *does* exist in current `chronos-forecasting` releases (confirmed on PyPI, up to 2.3.1) — the prior "nonexistent import" claim was stale — but it's still the wrong pipeline class for this model_id. Changed `predict.py`'s zero-shot fallback to use `ChronosPipeline`, matching `zero_shot.py`. This is the last-resort fallback path (used when the fine-tuned AutoGluon model isn't found), so it would only surface as a crash under that specific condition — but it means the "graceful fallback to zero-shot" the module's docstring promises has never actually worked. | Medium |
