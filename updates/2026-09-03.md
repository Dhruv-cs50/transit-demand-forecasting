Delegated three parallel, adversarial reads split by area (data ingestion +

| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `machine_learning_files/merge_pipeline.py` (`build_feature_store`, weather-merge `agg_kwargs`) | The monthly weather aggregation only ever copied 6 columns (`temp_f`, `precip_mm`, `windspeed_mph`, `is_raining`, `weather_code`, `cloud_cover_pct`) from `fetch_weather_openmeteo.py`'s output onto the feature store — never `humidity_pct` or `precip_in`, even though `fetch_weather_openmeteo.py`'s `_to_dataframe()` produces both for every station, and both are already listed as expected covariates in `models/chronos2/finetune.py`'s `KNOWN_FUTURE_COLS` (added 2026-08-31) and `Processing/ablation.py`'s `COVARIATE_GROUPS["weather"]`. So the model has been fine-tuned believing it has humidity and inches-of-precipitation signal that never actually reached it — every feature store this pipeline has produced was silently missing 2 of its documented weather covariates. This is the same "independently-maintained covariate lists drifting apart" class fixed repeatedly on 2026-08-30/31 and 2026-09-01, but this time the drift was between the consumer lists and the *producer* (`merge_pipeline.py`) rather than between the two consumer lists (which still match each other exactly, 71/71). Fixed by adding `precip_in=("precip_in", "mean")` and `humidity_pct=("humidity_pct", "mean")` to `agg_kwargs`, and added both (plus the already-silently-produced but undocumented `cloud_cover_pct`) to the module's own `Schema:` docstring, which had never listed any of the three. | Medium |
| 2 | `models/chronos2/predict.py` (`Predictor.forecast()`, final column selection) | `_zeroshot_forecast()` explicitly defends against Chronos not returning a named quantile column matching `p10`/`p90` (`keep = [c for c in [...] if c in preds_df.columns]`), and `forecast()`'s own clip loop three lines above the bug (`if col in preds.columns: preds[col] = preds[col].clip(...)`) shows the author knew these columns can be absent — but the function's actual `return` statement did an unconditional `preds[["timestamp", "station_id", "p10", "p50", "p90", ...]]` with no existence check, so a zero-shot run that dropped `p10` or `p90` would raise `KeyError` right at the finish line. Reached via `forecast_all_stations()` (used by `scheduler.py`'s nightly batch and `benchmarks.py`) this degrades to a silently-skipped station via the caller's try/except — but via `main()`'s single-station CLI path it's an unhandled crash. Fixed by filling any missing `p10`/`p50`/`p90` column with `NaN` in the same loop that already clips the present ones, so the final selection always succeeds and missing quantiles surface as `NaN` (matching how every downstream consumer already treats `NaN` in these columns) instead of crashing. | Medium |
| 3 | `website/charts.jsx` (`ROCCurve`) + `website/sections.jsx` (`Benchmarks`) | Both hardcoded the literal string `'AutoETS (AutoGluon)'` as the "is this the best/winning model" match key (bolding the leaderboard row, applying the accent color, swapping in a friendlier label). But `models/baselines/benchmarks.py` — whose `benchmark_leaderboard.csv` is exactly the file `scripts/export_website_data.py`'s `export_model_comparison()` reads first — writes this model's row as `"AutoGluon_Ensemble"`; `"AutoETS (AutoGluon)"` is never produced by any Python source in the repo (grepped `*.py`/`*.jsx`/`*.html`/`*.json`/`*.md` — it only appeared in `README.md`'s illustrative table and in the stale checked-in `website/data/model_comparison.json`, apparently a leftover from before the leaderboard-CSV export path existed). The site "looks right" today only because that stale JSON happens to carry the old label; the moment the pipeline is next actually run and `website/data/` is regenerated, the real `"AutoGluon_Ensemble"` row would silently lose its highlighting and pretty label (the numeric bestWAPE/bar-length math would stay correct — only the labeling/highlighting breaks). Fixed both files' match keys to `'AutoGluon_Ensemble'`, and updated the stale committed `website/data/model_comparison.json`'s `"model"` field to match, so the demo displays correctly both now and after the next real pipeline run. | Medium |

All three touched Python files re-`py_compile`d clean; the edited JSON re-parsed with `json.load` clean; grepped `website/` to confirm no remaining references to the old `'AutoETS (AutoGluon)'` string.
