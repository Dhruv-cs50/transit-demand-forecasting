| # | File(s) | Bug | Severity |
|---|---------|-----|----------|
| 1 | `Processing/feature_engineering.py` (`add_event_features` → `_add_monthly_event_features`) | `add_event_features()` only short-circuited on `events.empty`, not on an empty `df`. If `df` has zero rows (e.g. `merge_pipeline.py`'s `build_feature_store()` silently writes a 0-row `feature_store.parquet` when a `--start`/`--end` date filter excludes all BART data — it has no guard against this, just logs "0 rows, N columns"), the monthly-cadence path's `max(int(df["event_count"].max()), 1)` calls `int()` on `NaN` (an empty Series' `.max()`), raising `ValueError: cannot convert float NaN to integer`. Reproduced directly against the live code with an empty `df` and non-empty `events`: crashed before the fix, returned a clean 0-row DataFrame after. A realistic operational trap — re-running the pipeline with a stale date filter turns into an obscure crash several steps downstream instead of a clear "no data" message. Fixed by adding `df.empty` to the existing early-return guard. | Medium |
| 2 | `models/chronos2/finetune.py` (`KNOWN_FUTURE_COLS` / `_default_covariate_cols`) | The known-future covariate list included `hours_to_next_event`, which `feature_engineering.py`'s monthly-cadence path (the pipeline's actual production cadence, per `configs/model.yaml`'s `resample_freq: "MS"`) hardcodes to `np.nan` for every row — a 100%-NaN column fed to AutoGluon as a "known future" signal. Meanwhile the two columns that *are* populated with real monthly event signal — `hours_to_event` (game count for the month, from `merge_pipeline.py`'s `compute_event_features`) and `event_proximity_score` (0–1 proximity score, from the same monthly path) — were in neither the known-future nor past-only list, so AutoGluon never saw them at all. Verified with a repro importing `_default_covariate_cols` directly: before the fix, `event_proximity_score`/`hours_to_event` were absent from the returned column list despite being present in the input frame; after, both are included alongside the pre-existing (still-kept, since it's a real signal in non-monthly cadence) `hours_to_next_event`. Silently degrades fine-tuning quality rather than crashing — the two genuinely informative event columns were never trained on. | Medium |
| 3 | `Dockerfile.api` (CMD) | The file's own comment (`# Cloud Run injects PORT env var; default 8080`) and `README.md`'s Cloud Run section ("Exposes FastAPI on port `$PORT` (Cloud Run injects this env var)") both document that the container reads `$PORT`, but `CMD ["uvicorn", ..., "--port", "8080"]` used JSON exec form, which never invokes a shell and so never substitutes `$PORT` — the port was hardcoded to `8080` regardless of what Cloud Run actually injects. Currently latent: the README's documented `gcloud run deploy --port 8080` happens to match the hardcoded value, so today's deploy command works. It would silently fail Cloud Run's startup probe the moment anyone deploys with a different `--port` (or Cloud Run's injected default ever changes). Fixed by switching to shell form: `CMD ["sh", "-c", "uvicorn machine_learning_files.api:app --host 0.0.0.0 --port ${PORT:-8080}"]`, which now genuinely honors `$PORT` while keeping today's default. | Low-Medium (latent) |
