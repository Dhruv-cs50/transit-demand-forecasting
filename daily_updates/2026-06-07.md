# Daily Updates — 2026-06-07

## Bug Fixes

### 1. `Processing/feature_engineering.py` — Inverted sort guard (line ~140)
**Bug:** The rolling-weather block checked `if df["timestamp"].is_monotonic_increasing: df = df.sort_values(...)` — sorting only when already sorted (no-op), and skipping the sort when data was actually out of order.
**Fix:** Changed condition to `if not df["timestamp"].is_monotonic_increasing`.

### 2. `Processing/feature_engineering.py` — Broken `is_rain_onset` groupby fallback (line ~152)
**Bug:** When `station_id` was absent, the fallback passed `[True] * len(df)` (a Python list) as a groupby key, which would raise a `ValueError` at runtime.
**Fix:** Replaced the inline groupby expression with an explicit `if/else`: group-shift when `station_id` is present, plain `.shift(1)` when it is not.

### 3. `Processing/feature_engineering.py` — Dead `n_new` variable always zero (line ~442)
**Bug:** `n_new = n_features - len(df.columns)` subtracted the same value from itself, always producing 0. The count was never surfaced in logs.
**Fix:** Captured `n_cols_before = len(df.columns)` at the top of `build_features()`, then computed `n_new = n_features - n_cols_before` and included it in the log message.

### 4. `models/chronos2/predict.py` — Wrong Chronos class name `Chronos2Pipeline` (line ~123)
**Bug:** `_load_zeroshot()` imported `from chronos import Chronos2Pipeline`, which does not exist in the `chronos-forecasting` package. Every other call site correctly uses `ChronosPipeline`. This would raise `ImportError` at runtime when the zero-shot fallback path was triggered.
**Fix:** Changed to `from chronos import ChronosPipeline` (matches `zero_shot.py` and `api.py`).

### 5. `evaluation/validators.py` — `tz_localize(None)` on tz-aware timestamps (line ~372)
**Bug:** `check_station_coverage()` called `.dt.tz_localize(None)` unconditionally. The feature store schema stores timestamps as `datetime64[ns, America/Los_Angeles]`; calling `tz_localize` on an already-aware series raises `TypeError: Already tz-aware, use tz_convert to convert`.
**Fix:** Detect timezone first; use `.dt.tz_convert(None)` for tz-aware timestamps, leave tz-naive unchanged.

### 6. `machine_learning_files/api.py` — Double-localization on `as_of` string (line ~161)
**Bug:** `pd.Timestamp(as_of, tz="America/Los_Angeles")` raises `ValueError` when `as_of` is already a timezone-aware ISO string (e.g. `"2025-06-01T08:00:00-07:00"`), since you cannot pass `tz=` to a `Timestamp` constructor when the string already carries offset information.
**Fix:** Parse with `pd.Timestamp(as_of)` first, then branch: `tz_localize` if naive, `tz_convert` if already aware.
