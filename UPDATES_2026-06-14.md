# Daily Updates — 2026-06-14

## Bug Fixes

### 1. `tz_localize(None)` → `tz_convert(None)` (5 files, 9 occurrences)

`tz_localize(None)` adds timezone info to a naive Series/Timestamp; it raises a
`TypeError` when called on data that is already timezone-aware. All guarded blocks
of the form `if dt.tz is not None: … tz_localize(None)` are therefore guaranteed to
crash. The correct call to strip an existing timezone is `tz_convert(None)`.

**Files fixed:**
- `machine_learning_files/merge_pipeline.py` — lines 185, 191, 270, 286, 340
  - `compute_event_features`: both `ev_ts` and `ts_series` strips
  - `build_feature_store`: weather timestamp strip and base timestamp strip
  - `make_splits`: train/val/test timestamp strip
- `scripts/export_website_data.py` — lines 158, 221
  - `export_ridership_actuals`: single Timestamp strip
  - `export_model_comparison`: actuals Series strip
- `models/baselines/prophet_baseline.py` — lines 86, 235
  - `fit_station`: `ds` column used by Prophet must be tz-naive
  - `run_prophet_all_stations`: `last_ds` anchor for `predict_station`
- `evaluation/validators.py` — line 372
  - `check_station_coverage`: timestamp strip before `set_index`

### 2. Wrong `tz_localize` branch in `merge_pipeline.py` date filter (lines 313-316)

`build_feature_store` filtered rows using `pd.Timestamp(start, tz="America/Los_Angeles")`,
but `base["timestamp"]` at that point is tz-naive (transit timestamps come from
string-parsed period labels). The comparison raised `TypeError: Cannot compare tz-naive
and tz-aware datetime-like objects`. Removed the unnecessary `tz` argument from the
filter `Timestamp` constructors.

**File fixed:** `machine_learning_files/merge_pipeline.py`

### 3. Non-sequential index access in `check_missing_windows` (validators.py line 174)

After `grp.sort_values("timestamp")`, the DataFrame's integer index is preserved from
the parent DataFrame, not reset. The previous code used `grp.loc[idx - 1, "timestamp"]`
which silently returns the wrong row (or falls back to "unknown") whenever `idx - 1` is
not the positional predecessor. Fixed with positional lookup:
```python
pos = grp.index.get_loc(idx)
gap_start = str(grp.iloc[pos - 1]["timestamp"]) if pos > 0 else "unknown"
```

**File fixed:** `evaluation/validators.py`

### 4. `n_new` always computed as 0 in `build_features` (feature_engineering.py line 442)

`n_features = len(df.columns)` was set on line 441, then `n_new = n_features - len(df.columns)`
on line 442 — identical operands, always 0. Fixed by capturing `n_input_cols = len(df.columns)`
before the transformation chain begins, and also updated the log message to show the delta.

**File fixed:** `Processing/feature_engineering.py`

### 5. Wrong import module paths in `scheduler.py` (lines 98, 115, 128)

The nightly scheduler imported from non-existent modules:
- `ingestion.fetch_weather_openmeteo` → `machine_learning_files.fetch_weather_openmeteo`
- `ingestion.fetch_events` → `machine_learning_files.fetch_events`
- `processing.validators` → `evaluation.validators`

The renamed `load_config` import from the weather module now uses an alias
(`_wload_config`) to avoid shadowing the scheduler's own `load_config`.

Additionally, the merge pipeline script path `"processing/merge_pipeline.py"` was
incorrect (appears in both `NightlyPipeline.run()` and `main()`); corrected to
`"machine_learning_files/merge_pipeline.py"`.

**File fixed:** `models/baselines/scheduler.py`

### 6. `IndexError` in `Predictor.ridership_lift` (predict.py line 451)

`station_df[station_df["timestamp"] > now].iloc[0]` had no guard for an empty
result — if the feature store contains no future rows for the station, `.iloc[0]`
raises `IndexError`. Added `if not rain_rows.empty` check consistent with the
adjacent `future_row` check above it.

**File fixed:** `models/chronos2/predict.py`
